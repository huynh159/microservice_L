Docker Là Gì? Bản Chất & Nhu Cầu Thực Tế

Xóa bỏ rào cản môi trường dev/staging/production và chuẩn hóa đóng gói phần mềm

⚠️ Vấn Đề Thực Tế

"Trên máy tôi chạy được mà!" (Works on my machine) là nỗi ám ảnh kinh điển. Sự khác biệt giữa Java 17 và 21, thiếu thư viện native trên Linux, cấu hình database khác nhau khiến việc chuyển giao dự án dễ đổ vỡ.

Trong dự án: Cần chạy 4 backend service, 2 database PostgreSQL, Kafka, Zookeeper và Redis. Cài đặt thủ công từng phần mềm trên máy mới mất hàng giờ và dễ lỗi.
📦 Docker Giải Quyết Gì?

Docker đóng gói toàn bộ: mã nguồn chương trình, Java Runtime (JRE), thư viện phụ thuộc và cấu hình hệ điều hành vào một đơn vị độc lập gọi là Container. Chạy ổn định ở bất cứ nơi đâu có Docker Engine.

Lợi ích: Môi trường đồng nhất 100% giữa máy cá nhân của lập trình viên và máy chủ production.
🧱 4 Khái Niệm Cốt Lõi
• Image: Bản thiết kế (blueprint) tĩnh, đóng băng chỉ đọc chứa mã nguồn và môi trường.
• Container: Một instance đang thực thi của Image, có thể start/stop/restart.
• Registry: Kho lưu trữ Image (Docker Hub, GitHub Container Registry).
• Volume: Vùng lưu trữ bền vững gắn ngoài, dữ liệu không mất khi xóa container.
Áp dụng: Dùng Volume postgres_user_data giữ an toàn dữ liệu khách hàng.

Dockerfile & Kỹ Thuật Multi-Stage Build

Tối ưu dung lượng Image từ 800MB xuống 300MB và tuân thủ nguyên tắc bảo mật Non-Root

Quy Trình Multi-Stage Build Thực Tế Trong Dự Án Tiết kiệm 62% RAM/Disk
STAGE 1: BUILDER (~800MB)
Maven + JDK 21 Full
Tải dependencies, compile mã nguồn Java thành file .jar độc lập
➔
CHỈ COPY FILE .JAR
Bỏ lại toàn bộ Maven & Source
Không đem trình biên dịch hay source code vào môi trường chạy
➔
STAGE 2: RUNTIME (~300MB)
Eclipse Temurin JRE 21 Slim
Chỉ chứa môi trường thực thi tối thiểu, khởi động nhanh, bảo mật cao
📄 Dockerfile Mẫu Của user-service
# Stage 1: Build JAR
FROM maven:3.9-eclipse-temurin-21 AS builder
WORKDIR /app
COPY pom.xml . && COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: Minimal Runtime
FROM eclipse-temurin:21-jre-alpine
RUN adduser -D appuser && USER appuser
COPY --from=builder /app/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
🛡️ Bảo Mật Non-Root User (OWASP)

Mặc định, container chạy bằng quyền root. Nếu ứng dụng có lỗ hổng bảo mật (ví dụ: thực thi mã từ xa RCE), kẻ tấn công sẽ chiếm quyền root trên máy chủ chủ quản (Host OS).

Áp dụng vào dự án: Em tạo user appuser với quyền hạn tối thiểu và chuyển quyền bằng lệnh USER appuser trước khi chạy Spring Boot. Dù container bị tấn công, hacker cũng không thể can thiệp hệ thống.
Các chỉ dẫn cốt lõi: FROM (base image), COPY (chép file), RUN (thực thi lệnh build), ENTRYPOINT (lệnh khởi chạy cố định).

Thay vì chạy 8 câu lệnh docker run dài dòng với hàng chục tham số port/volume, file docker-compose.yml định nghĩa toàn bộ hạ tầng: chỉ cần docker compose up -d là toàn bộ hệ thống sẵn sàng.

Spring Security: Authentication & Authorization

Nguyên lý hoạt động của Security Filter Chain, Phân quyền RBAC và Xử lý mã lỗi HTTP

Luồng Xử Lý Request Qua Security Filter Chain
1. HTTP REQUEST
Header Authorization
Client gửi kèm Bearer <token>
➔
2. CUSTOM FILTER
JwtAuthenticationFilter
Rút trích token, xác minh chữ ký HMAC-SHA256
➔
3. SECURITY CONTEXT
SecurityContextHolder
Gán đối tượng UserPrincipal và Authorities (ROLE_USER, ROLE_ADMIN)
➔
4. CONTROLLER
@PreAuthorize
Thực thi nghiệp vụ hoặc chặn nếu không đủ quyền
🔑 2 Khái Niệm Then Chốt

• Authentication (Xác thực): Trả lời câu hỏi "Bạn là ai?". Kiểm tra email và mật khẩu hợp lệ.
• Authorization (Phân quyền): Trả lời câu hỏi "Bạn được phép làm gì?". Kiểm tra role người dùng trước khi gọi API.

⚖️ 401 Unauthorized vs 403 Forbidden

• HTTP 401 Unauthorized: Người dùng chưa chứng minh được danh tính (chưa đăng nhập, thiếu token hoặc token hết hạn).
• HTTP 403 Forbidden: Đã biết danh tính nhưng không đủ quyền hạn (User cố tình gọi API xóa tài khoản của Admin).

🎯 Áp Dụng Trong Dự Án

Sử dụng @PreAuthorize("hasRole('ADMIN')") để bảo vệ các API quản lý: chỉ có Admin mới được xem toàn bộ phòng chat hoặc mở quyền hỗ trợ. Khách hàng thông thường (ROLE_USER) bị chặn ngay với mã lỗi 403.

JWT: Cấu Trúc 3 Phần & Chiến Lược Dual-Token

Bản chất Stateless, Cơ chế chống giả mạo bằng Chữ ký số và Cặp Access/Refresh Token

🧩 Cấu Trúc 3 Phần Của JWT (Base64URL)
• Header (Đỏ): Chứa kiểu token (JWT) và thuật toán băm (HMAC-SHA256).
• Payload (Xanh): Chứa dữ liệu công khai (Claims): userId, email, roles, exp.
• Signature (Teal - Bảo mật cốt tử): Chữ ký số tạo bằng HMAC-SHA256(Header + Payload, SecretKey).
Chống giả mạo: Header và Payload chỉ mã hóa Base64 nên ai cũng đọc được. Nhưng nếu hacker sửa role từ USER thành ADMIN trong Payload, chữ ký Signature sẽ lập tức sai lệch và bị Spring Security từ chối!
🛡️ Tại Sao Cần Cả Access & Refresh Token?

Đây là bài toán cân bằng giữa Bảo mật và Trải nghiệm người dùng (UX):

• Nếu chỉ có 1 token dài hạn (30 ngày): Kẻ gian lấy được token sẽ chiếm quyền suốt 30 ngày mà server không thể thu hồi.
• Nếu chỉ có 1 token ngắn hạn (15 phút): Hết 15 phút, người dùng lại phải gõ lại password gây ức chế.
Giải pháp: Access Token (15 phút) gửi mỗi request; Refresh Token (7 ngày) nằm an toàn trong Database để cấp lại Access Token mới.
Tiêu chí Access Token Refresh Token
Thời gian sống Ngắn hạn: 15 phút (hạn chế rủi ro lộ lọt) Dài hạn: 7 ngày (tiện lợi cho người dùng)
Trạng thái lưu trữ Stateless: Không lưu database, server chỉ giải mã chữ ký Stateful: Lưu bản băm SHA-256 trong Database để kiểm soát
Mục đích sử dụng Đính kèm Header mọi request gọi API nghiệp vụ Chỉ dùng 1 việc duy nhất: Gửi lên /api/v1/auth/refresh để đổi token mới

Bảo Mật Nâng Cao: Token Rotation & Zero Enumeration

Cơ chế tự động phát hiện token bị đánh cắp và Phân biệt mục đích giữa SHA-256 vs BCrypt

Sơ Đồ Xoay Vòng Refresh Token (Token Rotation Workflow)
✓ KỊCH BẢN BÌNH THƯỜNG (NGƯỜI DÙNG HỢP LỆ)
1. Client gửi Refresh Token cũ lên server để xin cấp mới.
2. Server tìm bản băm SHA-256 trong DB ➔ Hợp lệ và chưa thu hồi.
3. Đánh dấu thu hồi token cũ + Cấp ngay 1 cặp Token hoàn toàn mới.
⚠️ KỊCH BẢN PHÁT HIỆN HACKER (REPLAY ATTACK)
1. Hacker lấy trộm token cũ và gửi lên để xin cấp Access Token.
2. Server tra cứu DB ➔ Phát hiện token này ĐÃ TỪNG BỊ THU HỒI!
3. Báo động đỏ: Lập tức hủy bỏ toàn bộ phiên làm việc của user đó.
🔒 Tại Sao Password Dùng BCrypt, Token Dùng SHA-256?
• Mật khẩu: Do người dùng đặt (ngắn, dễ đoán) ➔ Bắt buộc dùng BCrypt (có muối Salt ngẫu nhiên, thuật toán tính toán chậm để chống vét cạn Brute-force).
• Refresh Token: Chuỗi ngẫu nhiên 64 ký tự (bản thân nó đã đủ mạnh) ➔ Dùng SHA-256 để tìm kiếm WHERE token_hash = ? với tốc độ O(1) siêu tốc.
🛡️ Zero User Enumeration (Phòng Vệ Dò Email)

Nếu nhập sai password mà server báo "Mật khẩu không đúng", hacker sẽ biết email đó có thật trong hệ thống.

Áp dụng vào dự án: Dù email không tồn tại hay sai password, hệ thống luôn trả về cùng một thông báo chung: "Email hoặc mật khẩu không chính xác". Chống hacker quét dò danh sách email khách hàng.

Microservices: Phân Rã & 3 Nguyên Tắc Cốt Tử

Khắc phục điểm nghẽn của Monolith và triển khai mô hình Database-per-Service trong dự án

🏢 Monolith (Kiến Trúc Nguyên Khối)

Toàn bộ tính năng User, Chat, Notification đóng gói chung vào 1 file .war/.jar duy nhất và trỏ vào 1 database dùng chung.
Hạn chế chí mạng: Chỉ cần một lỗi rò rỉ bộ nhớ ở chức năng Chat có thể làm sập toàn bộ hệ thống, khiến việc Đăng nhập cũng ngưng trệ!

🚀 3 Nguyên Tắc Của Microservices
• Cách ly lỗi (Fault Isolation): Chat-service lỗi thì User-service vẫn vận hành bình thường.
• Triển khai độc lập (Independent Deployment): Cập nhật tính năng Chat không cần deploy lại User.
• Mở rộng linh hoạt (Targeted Scalability): Khi chat đông, chỉ cần nhân bản riêng container chat-service.
Tiêu chí Monolith (Nguyên Khối) Microservices (Vi Dịch Vụ - Dự Án)
Cơ sở dữ liệu 1 Database chung (khóa bảng ảnh hưởng lẫn nhau) Database-per-Service: users_db và chat_db độc lập
Ảnh hưởng sự cố 1 module lỗi có thể làm sập toàn bộ ứng dụng Cách ly hoàn toàn, lỗi không lan truyền dây chuyền
Độ phức tạp Đơn giản lúc đầu, phình to khó bảo trì về sau Cần kỹ thuật điều phối mạng, gateway và hàng đợi message
Hiện thực hóa trong dự án: Hệ thống chia thành 4 service riêng biệt: api-gateway (:8080), user-service (:8081), notification-service (:8082) và chat-service (:8083). Mỗi service sở hữu database riêng, giao tiếp qua REST và Kafka.

Giao Tiếp Giữa Các Service: Sync REST vs Async Kafka

Mô hình cây quyết định lựa chọn cơ chế giao tiếp phù hợp với từng bài toán nghiệp vụ

📞 Đồng Bộ: Synchronous (REST API)

Bên gửi gửi request HTTP và chờ đợi bên nhận phản hồi mới tiếp tục công việc.
• Ưu điểm: Đơn giản, nhận ngay kết quả để hiển thị giao diện.
• Nhược điểm: Khớp nối chặt (Coupling); nếu service nhận bị chậm sẽ làm nghẽn luôn service gửi.

Ví dụ dự án: Khi Admin mở phòng chat, chat-service gọi HTTP GET sang user-service lấy tên và avatar khách hàng.
📨 Bất Đồng Bộ: Asynchronous (Apache Kafka)

Bên gửi bắn sự kiện vào hàng đợi (Event Broker) rồi tiếp tục ngay lập tức mà không cần chờ đợi.
• Ưu điểm: Tách rời hoàn toàn (Decoupled); nếu bên nhận tạm chết thì tin nhắn vẫn nằm an toàn trên Kafka.
• Nhược điểm: Dữ liệu có độ trễ nhất định (Eventual Consistency).

Ví dụ dự án: Khi khách đăng ký tài khoản, user-service gửi event sang Kafka để notification-service gửi email ngầm.
Cây Quyết Định (Decision Rule): Khi Nào Dùng REST? Khi Nào Dùng Kafka?
Cần kết quả tức thì để hiển thị cho người dùng ➔ DÙNG REST API:
Ví dụ: Kiểm tra số dư tài khoản, lấy chi tiết hồ sơ cá nhân, truy vấn lịch sử đơn hàng.
Tác vụ xử lý tốn thời gian, không cần chờ kết quả ngay ➔ DÙNG KAFKA EVENT:
Ví dụ: Gửi email kích hoạt, xuất hóa đơn PDF, thông báo đẩy, cập nhật dữ liệu thống kê.

Apache Kafka: Nền Tảng Message Broker Phân Tán

4 khái niệm cốt lõi: Producer, Consumer, Topic Partition và Sức mạnh đệm chịu tải cao

Sơ Đồ Luồng Bắn Sự Kiện user-events Trong Dự Án
PRODUCER
user-service
Khách đăng ký ➔ Bắn event UserRegisteredEvent
➔
TOPIC & PARTITION
Topic: user-events
Lưu trữ log sự kiện bền vững theo thứ tự với Key = userId
➔
CONSUMER
notification-service
Đọc event từ Topic ➔ Gửi email chào mừng qua SMTP server
📤 Producer

Ứng dụng sản sinh và gửi thông điệp vào Kafka Broker. (Trong dự án: user-service).

📥 Consumer

Ứng dụng lắng nghe và kéo (pull) thông điệp về xử lý. (Trong dự án: notification-service).

🗂️ Topic

Kênh hàng đợi phân loại sự kiện. Chia thành nhiều Partition để tăng tốc đọc/ghi song song.

🖥️ Broker

Máy chủ Kafka đóng vai trò lưu trữ log thông điệp bền vững trên ổ đĩa, đảm bảo không mất dữ liệu.

Vì sao dùng Kafka thay vì gọi HTTP trực tiếp? Giảm khớp nối (Decoupling) và tăng độ bền: Nếu server gửi email bị quá tải hoặc sập tạm thời trong 15 phút, các sự kiện đăng ký tài khoản vẫn nằm an toàn trên Kafka chờ xử lý sau, người dùng đăng ký tài khoản hoàn toàn không bị gián đoạn!

Transactional Outbox Pattern & Idempotent Consumer

Triệt tiêu hoàn toàn rủi ro Dual-Write và Đảm bảo tính nhất quán dữ liệu (Eventual Consistency)

❌ Vấn Đề Dual-Write Nếu Gọi Trực Tiếp

Khi khách đăng ký: Nếu lưu User vào Database thành công, nhưng lệnh kafkaTemplate.send() bị rớt mạng ➔ User đã tạo nhưng email không bao giờ được gửi!
Ngược lại, nếu gửi Kafka trước rồi DB bị lỗi rollback ➔ Gửi email cho tài khoản không tồn tại!

💎 Giải Pháp: Transactional Outbox Pattern

Lưu User và Sự kiện gửi email vào bảng outbox_events trong CÙNG 1 DATABASE TRANSACTION. Cả 2 cùng thành công hoặc cùng rollback! Một tiến trình ngầm định kỳ quét bảng Outbox để xuất bản lên Kafka an toàn 100%.

Đảm bảo dữ liệu nghiệp vụ và event luôn đồng nhất trong PostgreSQL
➔
BƯỚC 2: SCHEDULER QUÉT

Đánh dấu PROCESSED

➔

Kiểm tra eventId

Giá trị đạt được: Đạt tiêu chuẩn phân tán At-Least-Once Delivery mà không sợ mất sự kiện ngay cả khi Kafka sập tạm thời.

Redis: Sức Mạnh Bộ Nhớ Đệm In-Memory RAM

Tốc độ truy xuất micro-giây, Tính năng tự động hết hạn TTL và So sánh với PostgreSQL

⚡ Tốc Độ Micro-giây

Lưu trữ toàn bộ trên bộ nhớ RAM, đọc ghi dưới 0.2 mili-giây, nhanh hơn hàng trăm lần so với đọc ghi trên ổ đĩa cứng (SSD/HDD).

⏱️ Tính Năng TTL

Time-To-Live: Tự động giải phóng và xóa key sau khoảng thời gian định sẵn (ví dụ 900s), không cần lập trình viên viết cronjob dọn rác.

🔑 Cấu Trúc Đa Dạng

Không chỉ là Key-Value chuỗi đơn thuần mà còn hỗ trợ Hash, Set, List, Sorted Set phục vụ cache phân tán và xếp hạng.

🛡️ Phòng Vệ Hệ Thống

Xử lý hàng trăm ngàn lệnh/giây giúp chặn đứng các đợt tấn công dò mật khẩu ngay tại tầng RAM trước khi chạm vào Database.

Tiêu chí so sánh PostgreSQL (Cơ Sở Dữ Liệu Quan Hệ) Redis (In-Memory Key-Value)
Môi trường lưu trữ Ổ cứng (Disk) ➔ Bền vững tuyệt đối (ACID) Bộ nhớ RAM ➔ Tốc độ siêu tốc, độ trễ cực thấp
Mục đích trong dự án Lưu thông tin tài khoản, mật khẩu băm, tin nhắn chat Cache hồ sơ user và Đếm số lần đăng nhập sai
Chịu tải tấn công Dễ cạn kiệt Connection Pool nếu bị spam request liên tục Chịu tải hàng trăm ngàn request/giây nhẹ nhàng
Triết lý thiết kế: Dùng đúng công cụ cho đúng bài toán — PostgreSQL cho lưu trữ nghiệp vụ lâu dài, Redis cho đệm tốc độ và phòng vệ cửa ngõ!

Áp Dụng Redis: Chống Brute-Force & Cache Hồ Sơ

Bảo vệ an toàn tài khoản với mã lỗi HTTP 429 và Khả năng chịu lỗi Graceful Degradation

🛡️ 1. Phòng Vệ Đăng Nhập Brute-Force (0.2ms)

Khi user đăng nhập thất bại: Tăng biến đếm login:attempts:{email} trong Redis và đặt TTL 900 giây (15 phút).
• Nếu sai ≥ 5 lần: Redis chặn ngay lập tức và ném lỗi HTTP 429 Too Many Requests.
• Nếu đăng nhập đúng: Xóa ngay key đó bằng lệnh DEL để reset bộ đếm về 0.
• Kết quả: Toàn bộ tải tấn công dò mật khẩu bị chặn đứng tại RAM, PostgreSQL không tốn 1% CPU!

⚡ 2. Cache Hồ Sơ & Chịu Lỗi (Graceful Degradation)

Khi Admin mở phòng chat, chat-service gọi sang lấy thông tin khách hàng: user-service đọc trực tiếp từ Spring Cache user:profile trong Redis chỉ mất 0.2ms.
• Kháng lỗi (Resilience): Cấu hình CacheErrorHandler tùy chỉnh. Nếu Redis tạm thời bị sập hoặc timeout, service tự động fallback đọc PostgreSQL và ghi log cảnh báo, tuyệt đối không quăng exception làm hỏng luồng chat!

Spring Cloud Gateway: Single Entry Point

Khắc phục 5 rủi ro khi gọi trực tiếp và Sức mạnh Netty Reactive phi phong tỏa

❌ 5 Rủi Ro Chí Mạng Khi Không Có Gateway
1. Lộ port nội bộ: Phải mở cổng 8081, 8082, 8083 ra ngoài Internet rất nguy hiểm.
2. CORS phức tạp: Từng service phải tự viết cấu hình CORS, dễ sai sót và xung đột.
3. Xác thực lặp thừa: Mỗi service lại phải parse JWT gây lãng phí tài nguyên CPU.
4. Mất dấu vết (Traceability): Không có điểm tập trung sinh mã truy vết xuyên suốt.
5. Khớp nối chặt (Coupling): Đổi IP/port nội bộ thì Frontend bắt buộc phải sửa code theo.
⚡ Netty Reactive vs Tomcat Truyền Thống
Tiêu chí Tomcat Blocking (Servlet) Netty Non-Blocking (Gateway)
Mô hình luồng 1 Request = 1 Thread cố định Event Loop phi phong tỏa
10.000 requests Cần 10.000 thread ➔ Tràn RAM Chỉ cần vài Thread lõi CPU
Phù hợp Xử lý CRUD nghiệp vụ nặng Làm Gateway chuyển tiếp lưu lượng
Công thức định tuyến: Route = Predicate (Khớp URL) + Filter (Xử lý tiền/hậu kỳ).
Vai trò trong dự án: Toàn bộ Frontend (React/Vue/Postman) chỉ cần kết nối duy nhất vào http://localhost:8080. Gateway đóng vai trò "người gác cổng" định tuyến thông minh vào trong.

Áp Dụng Gateway: Header Enrichment & Tracing

Định tuyến WebSocket ws://, Bơm header xác thực và Xử lý lỗi toàn cục ErrorWebExceptionHandler

💎 Kỹ Thuật Header Enrichment

Gateway giải mã token đúng 1 lần duy nhất, sau đó bóc tách dữ liệu và gắn vào Request Header trước khi chuyển tiếp vào các service nội bộ:

X-Trace-Id: "a1b2c3d4-e5f6-7890..."
X-User-Id: "987e6543-e21b-12d3..."
X-User-Email: "admin@company.com"
X-User-Roles: "ROLE_ADMIN"
Lợi ích vượt trội: Các service phía sau (user-service, chat-service) chỉ việc đọc Header là biết ai đang gọi mà không cần thư viện JWT hay giải mã lặp lại!
⚙️ Định Tuyến Thực Tế & Bắt Lỗi Toàn Cục
• Định tuyến REST: /api/v1/users/** ➔ :8081, /api/v1/chat/** ➔ :8083.
• Định tuyến WebSocket: /ws-chat/** chuyển sang ws://chat-service:8083 với giao thức WebSocket thuần Netty.
• CORS tập trung: Cấu hình globalcors cho phép mọi domain frontend gọi an toàn.
• ErrorWebExceptionHandler: Khi service nội bộ sập, Gateway tự động trả JSON chuẩn HTTP 503 kèm traceId, không hiển thị trang trắng HTML lỗi.

WebSocket & STOMP: Chat Realtime Admin – User

Vấn đề của HTTP Polling, Kết nối hai chiều Full-Duplex và Giao thức định tuyến STOMP

💡 Vấn Đề Thực Tế Của Chức Năng Chat

• Tình huống: Khách hàng gửi câu hỏi tư vấn trên web; Admin trực trên trang quản trị cần nhận được ngay; khi Admin trả lời, khách hàng phải nhìn thấy câu trả lời tức thời mà không cần bấm F5 tải lại trang.
• Hạn chế HTTP: HTTP chỉ có cơ chế Client hỏi ➔ Server đáp. Nếu muốn cập nhật, client phải liên tục gửi request thăm dò (Polling) mỗi 2 giây, sinh ra hàng ngàn request rỗng lãng phí băng thông và nghẽn máy chủ.

⚡ Giải Pháp: WebSocket & STOMP Broker

• WebSocket: Mở và duy trì 1 kết nối TCP hai chiều (Full-Duplex) duy nhất. Server có thể chủ động đẩy (push) tin nhắn mới xuống client bất kỳ lúc nào.
• Giao thức STOMP: Quy ước định dạng khung tin và định tuyến theo Destination:
- Kênh gửi lên server: /app/chat.sendMessage
- Kênh nhận tin theo phòng: /topic/rooms.{roomId}

Tiêu chí so sánh HTTP Polling Truyền Thống WebSocket + STOMP (Dự Án Đã Làm)
Cơ chế truyền tin Client hỏi liên tục mỗi 2-3s: "Có tin mới không?" Server chủ động đẩy tin ngay khi vừa nhận được
Độ trễ (Latency) 2 - 3 giây (phụ thuộc vào chu kỳ polling tiếp theo) Mili-giây: Gần như tức thời qua kết nối TCP đang mở
Tài nguyên hệ thống Tốn băng thông mạng vì hàng ngàn header HTTP lặp lại Cực kỳ tiết kiệm CPU máy chủ và băng thông mạng
Đơn vị điều phối: Dự án sử dụng In-Memory Simple Broker tích hợp sẵn của Spring Boot kích hoạt qua config.enableSimpleBroker("/topic", "/queue") để phân phối tin nhắn nhanh chóng mà không cần cài đặt thêm broker ngoài phức tạp.

Docker Là Gì? Bản Chất & Nhu Cầu Thực Tế

Xóa bỏ rào cản môi trường dev/staging/production và chuẩn hóa đóng gói phần mềm

⚠️ Vấn Đề Thực Tế

"Trên máy tôi chạy được mà!" (Works on my machine) là nỗi ám ảnh kinh điển. Sự khác biệt giữa Java 17 và 21, thiếu thư viện native trên Linux, cấu hình database khác nhau khiến việc chuyển giao dự án dễ đổ vỡ.

Trong dự án: Cần chạy 4 backend service, 2 database PostgreSQL, Kafka, Zookeeper và Redis. Cài đặt thủ công từng phần mềm trên máy mới mất hàng giờ và dễ lỗi.
📦 Docker Giải Quyết Gì?

Docker đóng gói toàn bộ: mã nguồn chương trình, Java Runtime (JRE), thư viện phụ thuộc và cấu hình hệ điều hành vào một đơn vị độc lập gọi là Container. Chạy ổn định ở bất cứ nơi đâu có Docker Engine.

Lợi ích: Môi trường đồng nhất 100% giữa máy cá nhân của lập trình viên và máy chủ production.
🧱 4 Khái Niệm Cốt Lõi
• Image: Bản thiết kế (blueprint) tĩnh, đóng băng chỉ đọc chứa mã nguồn và môi trường.
• Container: Một instance đang thực thi của Image, có thể start/stop/restart.
• Registry: Kho lưu trữ Image (Docker Hub, GitHub Container Registry).
• Volume: Vùng lưu trữ bền vững gắn ngoài, dữ liệu không mất khi xóa container.
Áp dụng: Dùng Volume postgres_user_data giữ an toàn dữ liệu khách hàng.

Dockerfile Là Gì?

Định nghĩa, cấu trúc và cách xây dựng Docker Image cho ứng dụng Spring Boot

Sơ Đồ Mối Quan Hệ: Từ Mã Nguồn Đến Thực Thể Đang Chạy Quy trình tự động hóa
BƯỚC 1: ĐẦU VÀO
Dockerfile + Source Code
Tệp văn bản chứa tập lệnh chỉ dẫn + file JAR / mã nguồn ứng dụng
docker build ➔
BƯỚC 2: ĐÓNG GÓI
Docker Image (Bản đóng băng)
Gói tĩnh, chỉ đọc (read-only) chứa ứng dụng, Java Runtime và dependencies
docker run ➔
BƯỚC 3: THỰC THI
Container (Instance Đang Chạy)
Một tiến trình độc lập, cô lập tài nguyên được tạo ra từ Docker Image
📄 Ví Dụ Dockerfile Spring Boot Thực Tế

Dockerfile đọc tuần tự từ trên xuống dưới; mỗi chỉ thị tạo một layer mới:

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
🛠️ Cách Build Image & Khởi Chạy Container: Terminal
# 1. Đọc Dockerfile tại (.) và tạo Image có tên:tag là my-spring-app:1.0
docker build -t my-spring-app:1.0 .

# 2. Khởi chạy Container từ Image, ánh xạ cổng 8080 host sang 8080 container
docker run --name my-spring-app -p 8080:8080 my-spring-app:1.0
• -t: Gán tag tên cho Image  |  .: Build context thư mục hiện tại  |  -p: Ánh xạ cổng HOST:CONTAINER.
🔍 Ý Nghĩa Từng Câu Lệnh Trong Dockerfile
FROM: Chọn base image có sẵn Java Runtime (JRE 21) gọn nhẹ, phù hợp chạy Spring Boot.
WORKDIR: Thiết lập thư mục làm việc mặc định /app bên trong container.
COPY: Chép file target/app.jar đã build từ máy host vào thư mục /app của image.
EXPOSE: Khai báo cổng 8080 ứng dụng lắng nghe (mang tính tài liệu, không tự mở cổng ra ngoài host).
ENTRYPOINT: Chỉ định lệnh mặc định cố định luôn được chạy khi container khởi động: java -jar app.jar.
Thứ tự thực thi: Khi docker build, Docker thực thi tuần tự từ trên xuống dưới để nung thành các lớp chỉ đọc (Layers). Khi docker run, container kích hoạt và khởi chạy lệnh tại ENTRYPOINT.
Các chỉ thị phổ biến khác: RUN (chạy lệnh cài đặt khi build), ENV (đặt biến môi trường), USER (đổi sang non-root user an toàn), CMD (tham số mặc định có thể bị ghi đè).

Docker Compose Là Gì?

Cấu hình và quản lý nhiều service bằng YAML trong một tệp duy nhất

Kiến Trúc Giao Tiếp: Client ➔ Backend (:8080) ➔ PostgreSQL (postgres:5432)
Mạng ảo: default (bridge) • DNS nội bộ tự động
🐙 Cấu Trúc File docker-compose.yml YAML Cú Pháp Chuẩn
services:
  backend:
    build: ./backend
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/todo_db
      SPRING_DATASOURCE_USERNAME: todo_user
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD}
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: todo_db
      POSTGRES_USER: todo_user
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U todo_user -d todo_db"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  postgres_data:

networks:
  default:
    driver: bridge
🚀 Lệnh Vận Hành Chính Với Docker Compose:
docker compose up --build -d # Build lại và khởi chạy nền
docker compose ps # Xem trạng thái & health của container
--build: Build lại image nếu code thay đổi  |  -d: Chạy detached ngầm  |  ps: Kiểm tra trạng thái.
📋 Ý Nghĩa Các Thuộc Tính Trong File Compose
services: Định nghĩa các container của ứng dụng (backend, postgres). Tên service cũng chính là Hostname nội bộ.
build & image: build: ./backend yêu cầu build từ Dockerfile; còn image kéo trực tiếp từ Docker Hub (PostgreSQL 17).
ports ("8080:8080"): Ánh xạ cổng HOST:CONTAINER. Cổng 8080 mở cho Client bên ngoài gọi; còn 5432 của DB được giữ kín trong mạng nội bộ.
environment & ${DB_PASSWORD}: Nạp biến môi trường cho container. Dùng biến ${DB_PASSWORD} từ file .env, tuyệt đối không hardcode mật khẩu.
volumes: Gắn ổ đĩa ảo postgres_data để dữ liệu database không bị mất khi container bị tắt hoặc tạo mới.
networks: Tạo mạng bridge ảo cho phép các service tự tìm thấy nhau thông qua Service Name.

Spring Security: Authentication & Authorization

Khái niệm cốt lõi, luồng xử lý request qua Filter Chain và ví dụ cấu hình SecurityFilterChain

Luồng Xử Lý Request Qua Spring Security Filter Chain Sơ đồ luồng 4 bước
1. CLIENT REQUEST
Gửi Yêu Cầu
Ví dụ: POST /api/login hoặc GET /api/admin
➔
2. FILTER CHAIN
SecurityFilterChain
Chặn bắt request, kiểm tra thông tin xác thực & quy tắc bảo mật
➔
3. AUTHENTICATION
Xác Thực Danh Tính
• 3A. Đã xác thực: Nạp SecurityContextHolder
• 3B. Chưa xác thực: Từ chối (401) / Login
➔
4. AUTHORIZATION
Kiểm Tra Quyền Hạn
• Cho phép: Role khớp ➔ Controller xử lý
• Từ chối: Thiếu quyền ➔ Trả HTTP 403
🔑 1. Authentication & Authorization Là Gì?
👤 Authentication (Xác thực)
Kiểm tra người dùng là ai:
• Nhập username/email + password.
• Hệ thống kiểm tra thông tin.
• Hợp lệ ➔ Xác định danh tính user.
🛡️ Authorization (Phân quyền)
Kiểm tra được phép làm gì:
• User chỉ xem/sửa dữ liệu của mình.
• Admin có quyền quản trị hệ thống.
• Không đủ quyền ➔ Từ chối truy cập.
⚖️ SO SÁNH: Authentication = "Bạn là ai?"  |  Authorization = "Bạn được làm gì?"
Ví dụ: Người dùng đăng nhập thành công nhưng vào trang quản trị bị chặn ➔ Xác thực thành công nhưng phân quyền thất bại (trả HTTP 403 Forbidden).
🧩 Các Thành Phần Cốt Lõi Trong Spring Security:
• SecurityFilterChain: Khai báo quy tắc lọc
• AuthenticationManager: Xử lý xác thực
• SecurityContextHolder: Lưu danh tính hiện tại
• GrantedAuthority: Biểu diễn Role/Quyền hạn
⚙️ 3. Ví Dụ Cấu Hình SecurityConfig Spring Boot 3
@Configuration
@EnableWebSecurity
public class SecurityConfig {
  @Bean
  public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
      .requestMatchers("/api/public/**").permitAll()
      .requestMatchers("/api/admin/**").hasRole("ADMIN")
      .anyRequest().authenticated()
    );
    return http.build();
  }
}
Cấu Hình Ý Nghĩa Chi Tiết
permitAll() Cho phép truy cập công khai mà không cần đăng nhập
hasRole("ADMIN") Yêu cầu người dùng phải có quyền/vai trò ROLE_ADMIN
authenticated() Yêu cầu người dùng bắt buộc đã xác thực danh tính
SecurityFilterChain Khai báo các quy tắc lọc và bảo mật cho HTTP request
💡 Lưu ý: Đoạn code trên minh họa phân quyền (Authorization). Cơ chế xác thực thực tế phụ thuộc cấu hình JWT Stateless hay Session. Không nên tắt CSRF một cách máy móc nếu ứng dụng dùng xác thực qua Cookie/Session trình duyệt.

⚖️ Chiến Lược Dual-Token (Access & Refresh) Cân bằng Security & UX

Giải quyết bài toán tiến thoái lưỡng nan: Token sống dài (30 ngày) dễ bị cướp quyền; Token sống ngắn (15 phút) bắt user đăng nhập liên tục gây khó chịu.

Tiêu Chí Access Token Refresh Token
Thời gian sống Ngắn hạn: 15 phút (hạn chế rủi ro lộ) Dài hạn: 7 ngày (trải nghiệm mượt mà)
Lưu trữ Stateless: Server không lưu DB, chỉ kiểm tra chữ ký Stateful: Lưu bản băm SHA-256 trong Database để thu hồi
Mục đích Gắn vào Header Bearer cho mọi API nghiệp vụ Chỉ gửi lên /api/v1/auth/refresh để đổi token mới
💡 Dự án áp dụng: Khi Access Token hết hạn, ứng dụng tự động gửi Refresh Token lấy cặp token mới mà người dùng không hề bị gián đoạn hay phải nhập lại mật khẩu.

Microservices: Phân Rã Kiến Trúc & 3 Lợi Ích Cốt Lõi

Khắc phục điểm nghẽn của Monolith và triển khai mô hình Database-per-Service trong dự án

🧩 Khái Niệm Microservices & Phân Chia Dự Án
Khái niệm cốt lõi: Kiến trúc phân rã ứng dụng thành các dịch vụ nhỏ độc lập (loose coupling), mỗi service phụ trách một nghiệp vụ riêng (Bounded Context), sở hữu database riêng và giao tiếp qua mạng (REST, WebSocket, Kafka).
Dự án của em chia làm 4 services độc lập:
• api-gateway (:8080): Cổng vào duy nhất
• user-service (:8081): Auth, User, Redis
• notification-service (:8082): Gửi email
• chat-service (:8083): Chat WebSocket
🚀 3 Lợi Ích Cốt Lõi Của Microservices
• Cách ly lỗi (Fault Isolation): Một service lỗi (như Chat lỗi bộ nhớ) thì User và Đăng nhập vẫn vận hành bình thường, không gây sập dây chuyền.
• Triển khai độc lập (Independent Deployment): Đội ngũ cập nhật tính năng Chat không cần build lại hay deploy lại toàn bộ User Service.
• Mở rộng có trọng điểm (Targeted Scalability): Khi lưu lượng chat tăng vọt, chỉ cần nhân bản (scale) riêng container chat-service mà không lãng phí tài nguyên.
Tiêu chí Monolith (Nguyên Khối) Microservices (Vi Dịch Vụ - Dự Án)
Cơ sở dữ liệu 1 Database chung (khóa bảng ảnh hưởng lẫn nhau) Database-per-Service: users_db và chat_db độc lập
Ảnh hưởng sự cố 1 module lỗi có thể làm sập toàn bộ ứng dụng Cách ly hoàn toàn, lỗi không lan truyền dây chuyền
Độ phức tạp Đơn giản lúc đầu, phình to khó bảo trì về sau Cần kỹ thuật điều phối mạng, gateway và hàng đợi message
Hiện thực hóa trong dự án: Hệ thống chia thành 4 service riêng biệt: api-gateway (:8080), user-service (:8081), notification-service (:8082) và chat-service (:8083). Mỗi service sở hữu database riêng, giao tiếp qua REST và Kafka.

Apache Kafka: Nền Tảng Message Broker Phân Tán

4 khái niệm cốt lõi: Producer, Consumer, Topic Partition và Sức mạnh đệm chịu tải cao

Sơ Đồ Luồng Bắn Sự Kiện user-events Trong Dự Án
PRODUCER
user-service
Khách đăng ký ➔ Bắn event UserRegisteredEvent
➔
TOPIC & PARTITION
Topic: user-events
Lưu trữ log sự kiện bền vững theo thứ tự với Key = userId
➔
CONSUMER
notification-service
Đọc event từ Topic ➔ Gửi email chào mừng qua SMTP server
📤 Producer

Ứng dụng sản sinh và gửi thông điệp vào Kafka Broker. (Trong dự án: user-service).

📥 Consumer

Ứng dụng lắng nghe và kéo (pull) thông điệp về xử lý. (Trong dự án: notification-service).

🗂️ Topic

Kênh hàng đợi phân loại sự kiện. Chia thành nhiều Partition để tăng tốc đọc/ghi song song.

🖥️ Broker

Máy chủ Kafka đóng vai trò lưu trữ log thông điệp bền vững trên ổ đĩa, đảm bảo không mất dữ liệu.

Vì sao dùng Kafka thay vì gọi HTTP trực tiếp? Giảm khớp nối (Decoupling) và tăng độ bền: Nếu server gửi email bị quá tải hoặc sập tạm thời trong 15 phút, các sự kiện đăng ký tài khoản vẫn nằm an toàn trên Kafka chờ xử lý sau, người dùng đăng ký tài khoản hoàn toàn không bị gián đoạn!

Redis Là Gì? Bản Chất Hoạt Động & So Sánh PostgreSQL

Kho dữ liệu In-Memory trên RAM, luồng Cache Hit / Miss, so sánh với PostgreSQL và 6 cấu trúc dữ liệu cốt lõi

⚡ 1. REDIS LÀ GÌ? BẢN CHẤT HOẠT ĐỘNG (CACHE HIT / CACHE MISS)
In-Memory RAM Store
Khái Niệm Cốt Lõi:
Redis là kho dữ liệu lưu trữ và xử lý trực tiếp trong bộ nhớ RAM, hỗ trợ nhiều cấu trúc dữ liệu và thao tác truy xuất siêu nhanh (< 1ms). Redis cũng hỗ trợ lưu xuống ổ đĩa (RDB / AOF) để phục hồi khi cần.
Ví Dụ Minh Họa: Hàng Nghìn Người Cùng Xem Sản Phẩm
🟢 Cache Hit: Có sẵn trong Redis ➔ Trả về ngay tức thì, giảm tải triệt để cho PostgreSQL.
🟡 Cache Miss: Chưa có ➔ Truy vấn PostgreSQL ➔ Trả về và lưu vào Redis kèm TTL cho lần sau.
⚖️ 2. Redis Khác PostgreSQL Như Thế Nào? So Sánh Trực Quan
Tiêu Chí Redis (In-Memory) PostgreSQL (RDBMS)
Mô hình Key-Value, cấu trúc đa dạng Quan hệ, bảng, hàng, cột & SQL
Nơi lưu Chủ yếu RAM (có thể lưu đĩa) Chủ yếu Ổ đĩa (dùng RAM đệm)
Truy xuất Rất nhanh (< 1ms trên RAM) Phụ thuộc query, index, tải, JOIN
Hết hạn Có TTL tự động dọn rác Thường phải tự thiết kế cơ chế xóa
Nghiệp vụ Cache sản phẩm, OTP, Session Tài khoản, đơn hàng, thanh toán
📌 Ví dụ dễ nhớ: PostgreSQL là nơi lưu hồ sơ chính thức của khách hàng; Redis giống khu vực lưu tạm những thông tin cần lấy liên tục để giảm thời gian truy xuất.
🧱 3. Các Cấu Trúc Dữ Liệu Nổi Bật Của Redis Data Types & Cú Pháp
String
Giá trị đơn giản: Cache, OTP, bộ đếm. SET otp:user 482691 EX 300 ➔ GET
Hash
Nhiều trường 1 đối tượng: Session, profile. HSET user:101 name "Huynh" ➔ HGET
List
Danh sách thứ tự: Hàng đợi đơn giản, tin gần đây. LPUSH recent user101 ➔ LRANGE
Set
Tập hợp duy nhất: Loại trùng, kiểm tra thành viên phòng chat. SADD room:1 u101 ➔ SISMEMBER
Sorted Set
Tập hợp có xếp hạng (Score): Bảng xếp hạng điểm. ZADD leaderboard 150 u101 ➔ ZREVRANGE
Streams
Luồng sự kiện: Xử lý theo thứ tự, consumer group. XADD orders * id 1001 status CREATED
💡 Điều Cần Nhớ: Redis không nhất thiết thay thế PostgreSQL mà hai công nghệ bổ trợ cho nhau. PostgreSQL lưu trữ dữ liệu nghiệp vụ chính thức lâu dài; Redis đảm nhận vai trò bộ đệm tốc độ cao và dữ liệu tạm thời có thời hạn (TTL).

4. Các Chức Năng Của Redis & Áp Dụng Thực Tế Trong Dự Án

5 chức năng phổ biến trong dự án và việc hiện thực hóa vào user-service: Cache hồ sơ, Chống Brute-force và Fallback an toàn

🎯 5 CHỨC NĂNG NỔI BẬT CỦA REDIS TRONG DỰ ÁN THỰC TẾ
5 Use Cases
1. Cache Tăng Tốc
Lưu kết quả truy vấn lặp lại (sản phẩm, profile), trả về tức thì, giảm tải database.
2. Session & Token
Lưu phiên dùng chung giữa nhiều instance; lưu refresh token hoặc danh sách token thu hồi.
3. OTP & Rate Limit
Lưu mã OTP với TTL 5 phút tự hủy; giới hạn số lần gọi API chống spam và quét mật khẩu.
4. Đếm & Xếp Hạng
Tăng bộ đếm nguyên tử INCR (lượt xem, like); Sorted Set tính điểm bảng xếp hạng.
5. Pub/Sub Realtime
Publish sự kiện lên channel; các service khác subscribe chuyển tiếp tới WebSocket.
⚡ Áp Dụng 1: Caching Hồ Sơ Người Dùng (GET /users/me) @Cacheable
• Vấn đề thực tế: Mỗi lần người dùng mở trang hoặc chuyển màn hình mobile, API GET /users/me lại được gọi. Nếu truy vấn PostgreSQL liên tục sẽ gây nghẽn database.
• Giải pháp Cache-Aside: Kiểm tra Redis trước ➔ Cache Hit trả về trong < 1ms ➔ Cache Miss truy vấn PostgreSQL rồi ghi vào Redis với TTL 10 phút.
• Đồng bộ dữ liệu (@CacheEvict): Khi người dùng đổi mật khẩu hoặc cập nhật tên, hàm kích hoạt @CacheEvict(key = "#userId") xóa ngay cache để lần sau đọc dữ liệu mới nhất, tránh Stale Data.
🛡️ Áp Dụng 2: Chống Brute-Force & Rate Limiting Đăng Nhập LoginAttemptService
🔢 Bộ Đếm Nguyên Tử (INCR trên RAM):
Khi nhập sai mật khẩu, gọi opsForValue().increment("login:attempts:" + email). Lệnh đếm trên RAM cực nhanh và an toàn tuyệt đối khi scale đa instance.
⏱️ Khóa Tự Động Với TTL 15 Phút:
Ở lần sai đầu tiên, đặt TTL 15 phút. Sau 15 phút, Redis tự động hủy bộ đếm và tự mở khóa tài khoản mà không cần viết lệnh dọn rác thủ công.
🚫 Chặn Đứng Tại Cửa Ngõ (HTTP 429):
Nếu số lần sai ≥ 5 lần, hệ thống lập tức từ chối và trả về mã HTTP 429 Too Many Requests, bảo vệ database an toàn khỏi các đợt dò mật khẩu.
💡 Tác Dụng An Toàn (Graceful Fallback): Dự án override CacheErrorHandler. Nếu Redis tạm thời mất kết nối hoặc quá tải, hệ thống không ném lỗi HTTP 500 mà tự động ghi log cảnh báo và Fallback đọc trực tiếp từ PostgreSQL, đảm bảo người dùng vẫn đăng nhập và sử dụng hệ thống bình thường.

WebSocket & STOMP: Khái Niệm, Bản Chất & Kiến Trúc

Phân biệt kết nối hai chiều WebSocket, giao thức tin nhắn STOMP và kiến trúc hệ thống Chat Admin – User

💬 1. Khái Niệm Cốt Lõi: WebSocket & STOMP Là Gì?
Khái Niệm Cốt Lõi
⚡ WebSocket — Kết Nối Hai Chiều Realtime:
Cho phép Client và Server trao đổi dữ liệu hai chiều liên tục trên một kết nối TCP duy nhất đã thiết lập, thay vì Client phải liên tục gửi HTTP request mới (Polling) gây lãng phí tài nguyên và chậm trễ.
📜 STOMP — Quy Ước Gửi Nhận Message:
Giao thức messaging định nghĩa các frame và lệnh chuẩn (CONNECT, SEND, SUBSCRIBE, MESSAGE), giúp Client đăng ký nhận tin và gửi tin đến các destination rõ ràng, tương thích chuẩn mực với Spring Boot.
🏛️ 2. Kiến Trúc Tổng Thể Hệ Thống Chat Realtime Admin – User Mô Hình Dự Án
📱 1. Client Giao Diện
React & React Native: Hiển thị danh sách hội thoại, khung chat và tin nhắn mới tức thời cho cả User và Admin mà không cần F5 tải lại trang.
⚡ 2. WebSocket + STOMP
Kết Nối TCP 2 Chiều: Mở và duy trì một đường truyền socket duy nhất liên tục giữa Client và Backend, truyền tải frame tin nhắn với độ trễ siêu thấp (< 1ms).
🛡️ 3. Chat Service & Auth
Bảo Mật & Kiểm Quyền: Trích xuất danh tính từ Principal phiên đăng nhập JWT (chống giả mạo), kiểm tra quyền phòng chat trước khi lưu và phát tin.
🗄️ 4. Broker & Database
Lưu Bền Vững & Đẩy Realtime: In-Memory Simple Broker phân phối tin nhắn đến đúng phòng chat; PostgreSQL lưu lịch sử tin nhắn lâu dài.
💡 Lưu Ý Quan Trọng: WebSocket có thể dùng trực tiếp mà không cần STOMP. Tuy nhiên, STOMP là lựa chọn chuẩn mực trên Spring Boot vì cung cấp sẵn mô hình Pub/Sub, destination routing và tích hợp mượt mà với Spring Security.

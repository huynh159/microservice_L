CHUYÊN ĐỀ 01 • TỔNG QUAN KIẾN TRÚC

Kiến Trúc Microservices: Nguyên Lý & Áp Dụng Thực Tế

Bản chất, ưu thế so với Monolith và mô hình 4 dịch vụ chuyên trách trong dự án

📖
1. Định Nghĩa & Bản Chất Kỹ Thuật

• Monolith (Kiến trúc nguyên khối): Toàn bộ module nghiệp vụ (Auth, Chat, Mail, User) đóng gói thành một ứng dụng duy nhất, dùng chung một cơ sở dữ liệu. Nhược điểm: Sự cố ở một chức năng (lỗi bộ nhớ, CPU cao) có thể làm tê liệt toàn bộ ứng dụng.
• Microservices (Kiến trúc vi dịch vụ): Phân rã hệ thống thành nhiều dịch vụ nhỏ độc lập theo từng nghiệp vụ. Mỗi dịch vụ chạy trên tiến trình riêng và kết nối với nhau qua giao thức mạng.

💡 Nguyên tắc cốt lõi: Độc lập triển khai (Independent Deployment), Trách nhiệm đơn lẻ (Single Responsibility), và Cơ sở dữ liệu riêng (Database-per-Service).
🎯
2. Lợi Ích Cốt Lõi So Với Monolith
  • ■ Cách ly lỗi, không sập dây chuyền (Fault Isolation): Nếu dịch vụ Chat hoặc Notification gặp sự cố, dịch vụ User và Gateway vẫn hoạt động bình thường, phục vụ người dùng đăng nhập.
  • ■ Triển khai độc lập (Independent Deployment): Cập nhật tính năng Chat chỉ cần build và deploy lại Chat Service, không ảnh hưởng hay làm gián đoạn các dịch vụ khác.
  • ■ Mở rộng linh hoạt (Targeted Scalability): Khi lưu lượng chat tăng cao, chỉ cần nhân bản thêm container Chat Service, tối ưu hóa tài nguyên RAM/CPU máy chủ.

CHUYÊN ĐỀ 03.1 • AUTHENTICATION & SECURITY

Bảo Mật JWT: Định Nghĩa, Thuật Toán Băm & Phân Quyền

Bản chất Access vs Refresh Token, Cơ chế chữ ký HMAC-SHA256 chống giả mạo và phân quyền User / Admin

🎫
1. Định Nghĩa: Access Token vs Refresh Token
• Access Token (15m - Stateless): Chuỗi JWT tự chứa danh tính (User ID, Email, Roles). Gửi qua Header Authorization: Bearer mỗi khi gọi API. Server không lưu DB, chỉ cần Secret Key là giải mã xác thực tức thì trong 0.1ms. Nhược điểm: không thể thu hồi ngay, nên TTL bắt buộc phải ngắn.
• Refresh Token (7d - Stateful): Chuỗi ngẫu nhiên 64 ký tự hex (độ hỗn loạn cao). Chỉ dùng duy nhất 1 việc: xin cấp lại Access Token mới khi hết hạn mà không bắt user đăng nhập lại. Server lưu bản băm SHA-256 trong DB để quản lý phiên.
🔐
2. Cấu Trúc 3 Phần & Thuật Toán HMAC-SHA256
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJyb2xlcyI6WyJBRE1JTiJdfQ.s4gK_Xq-90_signature

• Header & Payload: Chỉ là mã hóa Base64URL (dạng đọc được công khai, không phải mã hóa bí mật). Bất kỳ ai cũng đọc được claim sub, roles.

• Signature (Chữ ký số - Nơi bảo mật thực sự):
Signature = HMAC-SHA256(Base64(Header) + "." + Base64(Payload), SecretKey)
Chống sửa quyền: Nếu kẻ xấu tự sửa ROLE_USER thành ROLE_ADMIN, Signature do Server tính lại bằng SecretKey sẽ sai lệch ➔ Chặn đứng ngay lập tức!

⚙️
3. Mã Băm Trong Hệ Thống: BCrypt vs SHA-256
• Mật khẩu người dùng ➔ Dùng BCrypt: Thuật toán băm một chiều có sinh Salt ngẫu nhiên và tốc độ chậm (~100ms) để chống tấn công vét cạn (Brute-force) và tra cứu từ điển (Rainbow Table) đối với mật khẩu ngắn.
• Refresh Token trong DB ➔ Dùng SHA-256: Token vốn là chuỗi 64 ký tự ngẫu nhiên (không thể vét cạn). Ta băm SHA-256 để: (1) Nếu DB bị lộ, hacker chỉ thấy chuỗi băm vô dụng; (2) Tốc độ băm cực nhanh (<1ms), tạo B-Tree Index tra cứu O(1) tức thì.
🛡️
4. Cơ Chế Phân Quyền RBAC (User vs Admin)
• Trích xuất quyền: JwtAuthenticationFilter đọc claim "roles": ["ROLE_ADMIN"] từ token ➔ Chuyển thành GrantedAuthority nạp vào SecurityContextHolder.
• Kiểm soát API: Dùng @PreAuthorize("hasRole('ADMIN')") tại Controller hoặc .requestMatchers("/api/v1/users/**").hasRole("ADMIN") tại FilterChain.
Phân biệt 2 mã lỗi HTTP:
• 401 Unauthorized: Thiếu token hoặc token hết hạn (Chưa xác thực danh tính).
• 403 Forbidden: Đã có token hợp lệ nhưng role là USER cố tình gọi API xóa của ADMIN (Không đủ quyền hạn).
CHUYÊN ĐỀ 03.2 • ADVANCED TOKEN SECURITY

Chiến Lược Token Rotation & Chống Chiếm Đoạt Phiên

Sự khác biệt cốt tử giữa SHA-256 vs BCrypt, Tự động phát hiện token bị đánh cắp

SƠ ĐỒ XOAY VÒNG REFRESH TOKEN (TOKEN ROTATION WORKFLOW) Nguyên lý Zero-Knowledge
✓ KỊCH BẢN 1: NGƯỜI DÙNG HỢP LỆ ĐỔI TOKEN MỚI
1. Client gửi Refresh Token cũ lên /api/v1/auth/refresh.
2. Server băm SHA-256 tìm trong database ➔ Token chưa bị thu hồi.
3. Thu hồi token cũ (đánh dấu revoked_at) + Cấp Refresh Token mới.
➔ Token cũ lập tức bị vô hiệu hóa (Revoked), hacker có lấy được token cũ cũng hoàn toàn vô dụng!
⚠️ KỊCH BẢN 2: PHÁT HIỆN HACKER TÁI SỬ DỤNG TOKEN
1. Hacker lấy được token cũ và gửi lên để xin cấp mới.
2. Server kiểm tra DB ➔ Phát hiện token này ĐÃ TỪNG BỊ THU HỒI!
3. BẬT BÁO ĐỘNG ĐỎ: Có kẻ gian đang dùng token đánh cắp.
➔ Lập tức từ chối HTTP 401 và có thể thu hồi toàn bộ phiên của tài khoản này!
🔒
Tại Sao Token Dùng SHA-256 Còn Pass Dùng BCrypt?

• Mật khẩu: Người dùng đặt ngắn, dễ đoán ➔ Cần BCrypt (có salt ngẫu nhiên, cố tình tính toán chậm để chống vét cạn Brute-force).

• Refresh Token: Là chuỗi ngẫu nhiên 64 ký tự (bản thân nó đã cực mạnh) ➔ Dùng SHA-256 (hàm tất định) để có thể đánh index và tìm kiếm WHERE token_hash = ? với tốc độ O(1)!

🛡️
Thu Hồi Khi Đổi Mật Khẩu & Zero Enumeration

• Đổi mật khẩu: Lập tức gọi revokeAllByUserId(userId) xóa sổ toàn bộ phiên đăng nhập trên mọi thiết bị, buộc đăng nhập lại.

• Zero User Enumeration: Dù email không tồn tại hay sai password, hệ thống luôn trả cùng 1 thông điệp: "Email hoặc mật khẩu không chính xác" (chống hacker dò email tồn tại).

Token Relay & Kháng Lỗi (Graceful Degradation)

• Token Relay: Khi Admin xem chi tiết chat, chat-service gọi HTTP sang user-service và truyền tiếp (relay) Token trong header để lấy thông tin khách hàng.

• Graceful Degradation: Nếu user-service chẳng may bị chậm hoặc gián đoạn, chat-service tự động dùng thông tin fallback ("Khách ẩn danh"), bảo đảm chức năng chat không bị ngắt quãng!

Vấn Đề Dual-Write Nếu Không Có Outbox

Nếu lưu User vào Database xong rồi gọi Kafka trực tiếp: Lỡ Kafka bị rớt mạng đúng lúc đó ➔ User đã tạo nhưng email không bao giờ được gửi!

➔ Với Outbox: Dữ liệu event nằm an toàn trong bảng outbox_events. Khi Kafka phục hồi kết nối, processor sẽ tiếp tục đẩy đi ➔ Zero Data Loss!

⚙️
Idempotent Consumer & Dead Letter Topic

• Idempotent Consumer: Nếu mạng chập chờn Kafka gửi lại sự kiện lần 2, notification-service kiểm tra thấy eventId này đã gửi rồi ➔ bỏ qua, chống gửi 2 email rác cho khách.

• Dead Letter Topic (DLT): Các event bị lỗi nghiêm trọng (JSON sai cú pháp) sẽ tự động được cách ly sang user-events.DLT để lập trình viên kiểm tra sau mà không làm nghẽn luồng chính.

CHUYÊN ĐỀ 07.1 • REVENUE & ROUTING

Spring Cloud Gateway: Cửa Ngõ Hệ Thống

Khắc phục 5 rủi ro khi gọi trực tiếp Microservices và Sức mạnh của Netty Reactive Event Loop

❌
5 Rủi Ro Chí Mạng Khi Không Có Gateway

1. Lộ sơ đồ mạng: Phải mở port 8081, 8082, 8083 ra ngoài Internet ➔ Bề mặt tấn công cực rộng.

2. CORS phức tạp: Từng service phải tự viết cấu hình CORS, dễ sai sót và xung đột.

3. Xác thực lặp thừa: Mỗi service lại phải giải mã JWT, kiểm tra quyền ➔ Lãng phí CPU máy chủ.

4. Mất dấu truy vết (Traceability): Không có điểm tập trung sinh X-Trace-Id ngay từ đầu.

5. Khớp nối chặt (Coupling): Đổi IP hay port service nội bộ thì Frontend bắt buộc phải sửa code theo.

⚡

Kỹ Thuật Header Enrichment

Gateway giải mã token đúng 1 lần duy nhất, sau đó bóc tách dữ liệu và gắn vào Header trước khi chuyển tiếp:

X-Trace-Id: "a1b2c3d4-e5f6..."
X-User-Id: "987e6543-e21b..."
X-User-Email: "admin@company.com"
X-User-Roles: "ROLE_ADMIN"

➔ user-service và chat-service chỉ việc đọc Header là biết ai đang gọi, không cần dependency JWT!

🚨
ErrorWebExceptionHandler Toàn Cục

• Trong Spring Cloud Gateway (Netty), @RestControllerAdvice không hoạt động vì không có Spring MVC!

• Sử dụng ErrorWebExceptionHandler với độ ưu tiên @Order(-2) để bắt trọn mọi exception.

• Khi backend service bị sập ➔ Gateway tự động trả về JSON chuẩn HTTP 503 Service Unavailable (kèm traceId), tuyệt đối không hiển thị trang trắng HTML lỗi.

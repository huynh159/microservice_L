Docker Là Gì? Bản Chất & Nhu Cầu Thực Tế

Xóa bỏ rào cản môi trường dev/staging/production và chuẩn hóa đóng gói phần mềm

⚠️ Vấn Đề Thực Tế

"Trên máy tôi chạy được mà!" (Works on my machine) là nỗi ám ảnh kinh điển. Sự khác biệt giữa Java 17 và 21, thiếu thư viện native trên Linux, cấu hình database khác nhau khiến việc chuyển giao dự án dễ đổ vỡ.

Trong dự án: Cần chạy 4 backend service, 2 database PostgreSQL, Kafka, Zookeeper và Redis. Cài đặt thủ công từng phần mềm trên máy mới mất hàng giờ và dễ lỗi.
📦 Docker Giải Quyết Gì?

Docker đóng gói toàn bộ: mã nguồn chương trình, Java Runtime (JRE), thư viện phụ thuộc và cấu hình hệ điều hành vào một đơn vị độc lập gọi là Container. Chạy ổn định ở bất cứ nơi đâu có Docker Engine.

Lợi ích: Môi trường đồng nhất 100% giữa máy cá nhân của lập trình viên và máy chủ production.
🧱 4 Khái Niệm Cốt Lõi
• Image: Bản thiết kế (blueprint) tĩnh, đóng băng chỉ đọc chứa mã nguồn và môi trường.
• Container: Một instance đang thực thi của Image, có thể start/stop/restart.
• Registry: Kho lưu trữ Image (Docker Hub, GitHub Container Registry).
• Volume: Vùng lưu trữ bền vững gắn ngoài, dữ liệu không mất khi xóa container.
Áp dụng: Dùng Volume postgres_user_data giữ an toàn dữ liệu khách hàng.

Dockerfile Là Gì?

Định nghĩa, cấu trúc và cách xây dựng Docker Image cho ứng dụng Spring Boot

Sơ Đồ Mối Quan Hệ: Từ Mã Nguồn Đến Thực Thể Đang Chạy Quy trình tự động hóa
BƯỚC 1: ĐẦU VÀO
Dockerfile + Source Code
Tệp văn bản chứa tập lệnh chỉ dẫn + file JAR / mã nguồn ứng dụng
docker build ➔
BƯỚC 2: ĐÓNG GÓI
Docker Image (Bản đóng băng)
Gói tĩnh, chỉ đọc (read-only) chứa ứng dụng, Java Runtime và dependencies
docker run ➔
BƯỚC 3: THỰC THI
Container (Instance Đang Chạy)
Một tiến trình độc lập, cô lập tài nguyên được tạo ra từ Docker Image
📄 Ví Dụ Dockerfile Spring Boot Thực Tế

Dockerfile đọc tuần tự từ trên xuống dưới; mỗi chỉ thị tạo một layer mới:

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
🛠️ Cách Build Image & Khởi Chạy Container: Terminal
# 1. Đọc Dockerfile tại (.) và tạo Image có tên:tag là my-spring-app:1.0
docker build -t my-spring-app:1.0 .

# 2. Khởi chạy Container từ Image, ánh xạ cổng 8080 host sang 8080 container
docker run --name my-spring-app -p 8080:8080 my-spring-app:1.0
• -t: Gán tag tên cho Image  |  .: Build context thư mục hiện tại  |  -p: Ánh xạ cổng HOST:CONTAINER.
🔍 Ý Nghĩa Từng Câu Lệnh Trong Dockerfile
FROM: Chọn base image có sẵn Java Runtime (JRE 21) gọn nhẹ, phù hợp chạy Spring Boot.
WORKDIR: Thiết lập thư mục làm việc mặc định /app bên trong container.
COPY: Chép file target/app.jar đã build từ máy host vào thư mục /app của image.
EXPOSE: Khai báo cổng 8080 ứng dụng lắng nghe (mang tính tài liệu, không tự mở cổng ra ngoài host).
ENTRYPOINT: Chỉ định lệnh mặc định cố định luôn được chạy khi container khởi động: java -jar app.jar.
Thứ tự thực thi: Khi docker build, Docker thực thi tuần tự từ trên xuống dưới để nung thành các lớp chỉ đọc (Layers). Khi docker run, container kích hoạt và khởi chạy lệnh tại ENTRYPOINT.
Các chỉ thị phổ biến khác: RUN (chạy lệnh cài đặt khi build), ENV (đặt biến môi trường), USER (đổi sang non-root user an toàn), CMD (tham số mặc định có thể bị ghi đè).

Docker Compose Là Gì?

Cấu hình và quản lý nhiều service bằng YAML trong một tệp duy nhất

Kiến Trúc Giao Tiếp: Client ➔ Backend (:8080) ➔ PostgreSQL (postgres:5432)
Mạng ảo: default (bridge) • DNS nội bộ tự động
🐙 Cấu Trúc File docker-compose.yml YAML Cú Pháp Chuẩn
services:
  backend:
    build: ./backend
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/todo_db
      SPRING_DATASOURCE_USERNAME: todo_user
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD}
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: todo_db
      POSTGRES_USER: todo_user
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U todo_user -d todo_db"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  postgres_data:

networks:
  default:
    driver: bridge
🚀 Lệnh Vận Hành Chính Với Docker Compose:
docker compose up --build -d # Build lại và khởi chạy nền
docker compose ps # Xem trạng thái & health của container
--build: Build lại image nếu code thay đổi  |  -d: Chạy detached ngầm  |  ps: Kiểm tra trạng thái.
📋 Ý Nghĩa Các Thuộc Tính Trong File Compose
services: Định nghĩa các container của ứng dụng (backend, postgres). Tên service cũng chính là Hostname nội bộ.
build & image: build: ./backend yêu cầu build từ Dockerfile; còn image kéo trực tiếp từ Docker Hub (PostgreSQL 17).
ports ("8080:8080"): Ánh xạ cổng HOST:CONTAINER. Cổng 8080 mở cho Client bên ngoài gọi; còn 5432 của DB được giữ kín trong mạng nội bộ.
environment & ${DB_PASSWORD}: Nạp biến môi trường cho container. Dùng biến ${DB_PASSWORD} từ file .env, tuyệt đối không hardcode mật khẩu.
volumes: Gắn ổ đĩa ảo postgres_data để dữ liệu database không bị mất khi container bị tắt hoặc tạo mới.
networks: Tạo mạng bridge ảo cho phép các service tự tìm thấy nhau thông qua Service Name.

Spring Security: Authentication & Authorization

Khái niệm cốt lõi, luồng xử lý request qua Filter Chain và ví dụ cấu hình SecurityFilterChain

Luồng Xử Lý Request Qua Spring Security Filter Chain Sơ đồ luồng 4 bước
1. CLIENT REQUEST
Gửi Yêu Cầu
Ví dụ: POST /api/login hoặc GET /api/admin
➔
2. FILTER CHAIN
SecurityFilterChain
Chặn bắt request, kiểm tra thông tin xác thực & quy tắc bảo mật
➔
3. AUTHENTICATION
Xác Thực Danh Tính
• 3A. Đã xác thực: Nạp SecurityContextHolder
• 3B. Chưa xác thực: Từ chối (401) / Login
➔
4. AUTHORIZATION
Kiểm Tra Quyền Hạn
• Cho phép: Role khớp ➔ Controller xử lý
• Từ chối: Thiếu quyền ➔ Trả HTTP 403
🔑 1. Authentication & Authorization Là Gì?
👤 Authentication (Xác thực)
Kiểm tra người dùng là ai:
• Nhập username/email + password.
• Hệ thống kiểm tra thông tin.
• Hợp lệ ➔ Xác định danh tính user.
🛡️ Authorization (Phân quyền)
Kiểm tra được phép làm gì:
• User chỉ xem/sửa dữ liệu của mình.
• Admin có quyền quản trị hệ thống.
• Không đủ quyền ➔ Từ chối truy cập.
⚖️ SO SÁNH: Authentication = "Bạn là ai?"  |  Authorization = "Bạn được làm gì?"
Ví dụ: Người dùng đăng nhập thành công nhưng vào trang quản trị bị chặn ➔ Xác thực thành công nhưng phân quyền thất bại (trả HTTP 403 Forbidden).
🧩 Các Thành Phần Cốt Lõi Trong Spring Security:
• SecurityFilterChain: Khai báo quy tắc lọc
• AuthenticationManager: Xử lý xác thực
• SecurityContextHolder: Lưu danh tính hiện tại
• GrantedAuthority: Biểu diễn Role/Quyền hạn
⚙️ 3. Ví Dụ Cấu Hình SecurityConfig Spring Boot 3
@Configuration
@EnableWebSecurity
public class SecurityConfig {
  @Bean
  public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
      .requestMatchers("/api/public/**").permitAll()
      .requestMatchers("/api/admin/**").hasRole("ADMIN")
      .anyRequest().authenticated()
    );
    return http.build();
  }
}
Cấu Hình Ý Nghĩa Chi Tiết
permitAll() Cho phép truy cập công khai mà không cần đăng nhập
hasRole("ADMIN") Yêu cầu người dùng phải có quyền/vai trò ROLE_ADMIN
authenticated() Yêu cầu người dùng bắt buộc đã xác thực danh tính
SecurityFilterChain Khai báo các quy tắc lọc và bảo mật cho HTTP request
💡 Lưu ý: Đoạn code trên minh họa phân quyền (Authorization). Cơ chế xác thực thực tế phụ thuộc cấu hình JWT Stateless hay Session. Không nên tắt CSRF một cách máy móc nếu ứng dụng dùng xác thực qua Cookie/Session trình duyệt.

⚖️ Chiến Lược Dual-Token (Access & Refresh) Cân bằng Security & UX

Giải quyết bài toán tiến thoái lưỡng nan: Token sống dài (30 ngày) dễ bị cướp quyền; Token sống ngắn (15 phút) bắt user đăng nhập liên tục gây khó chịu.

Tiêu Chí Access Token Refresh Token
Thời gian sống Ngắn hạn: 15 phút (hạn chế rủi ro lộ) Dài hạn: 7 ngày (trải nghiệm mượt mà)
Lưu trữ Stateless: Server không lưu DB, chỉ kiểm tra chữ ký Stateful: Lưu bản băm SHA-256 trong Database để thu hồi
Mục đích Gắn vào Header Bearer cho mọi API nghiệp vụ Chỉ gửi lên /api/v1/auth/refresh để đổi token mới
💡 Dự án áp dụng: Khi Access Token hết hạn, ứng dụng tự động gửi Refresh Token lấy cặp token mới mà người dùng không hề bị gián đoạn hay phải nhập lại mật khẩu.

Microservices: Phân Rã & 3 Nguyên Tắc Cốt Tử

Khắc phục điểm nghẽn của Monolith và triển khai mô hình Database-per-Service trong dự án

🏢 Monolith (Kiến Trúc Nguyên Khối)

Toàn bộ tính năng User, Chat, Notification đóng gói chung vào 1 file .war/.jar duy nhất và trỏ vào 1 database dùng chung.
Hạn chế chí mạng: Chỉ cần một lỗi rò rỉ bộ nhớ ở chức năng Chat có thể làm sập toàn bộ hệ thống, khiến việc Đăng nhập cũng ngưng trệ!

🚀 3 Nguyên Tắc Của Microservices
• Cách ly lỗi (Fault Isolation): Chat-service lỗi thì User-service vẫn vận hành bình thường.
• Triển khai độc lập (Independent Deployment): Cập nhật tính năng Chat không cần deploy lại User.
• Mở rộng linh hoạt (Targeted Scalability): Khi chat đông, chỉ cần nhân bản riêng container chat-service.
Tiêu chí Monolith (Nguyên Khối) Microservices (Vi Dịch Vụ - Dự Án)
Cơ sở dữ liệu 1 Database chung (khóa bảng ảnh hưởng lẫn nhau) Database-per-Service: users_db và chat_db độc lập
Ảnh hưởng sự cố 1 module lỗi có thể làm sập toàn bộ ứng dụng Cách ly hoàn toàn, lỗi không lan truyền dây chuyền
Độ phức tạp Đơn giản lúc đầu, phình to khó bảo trì về sau Cần kỹ thuật điều phối mạng, gateway và hàng đợi message
Hiện thực hóa trong dự án: Hệ thống chia thành 4 service riêng biệt: api-gateway (:8080), user-service (:8081), notification-service (:8082) và chat-service (:8083). Mỗi service sở hữu database riêng, giao tiếp qua REST và Kafka.

Giao Tiếp Giữa Các Service: Sync REST vs Async Kafka

Mô hình cây quyết định lựa chọn cơ chế giao tiếp phù hợp với từng bài toán nghiệp vụ

📞 Đồng Bộ: Synchronous (REST API)

Bên gửi gửi request HTTP và chờ đợi bên nhận phản hồi mới tiếp tục công việc.
• Ưu điểm: Đơn giản, nhận ngay kết quả để hiển thị giao diện.
• Nhược điểm: Khớp nối chặt (Coupling); nếu service nhận bị chậm sẽ làm nghẽn luôn service gửi.

Ví dụ dự án: Khi Admin mở phòng chat, chat-service gọi HTTP GET sang user-service lấy tên và avatar khách hàng.
📨 Bất Đồng Bộ: Asynchronous (Apache Kafka)

Bên gửi bắn sự kiện vào hàng đợi (Event Broker) rồi tiếp tục ngay lập tức mà không cần chờ đợi.
• Ưu điểm: Tách rời hoàn toàn (Decoupled); nếu bên nhận tạm chết thì tin nhắn vẫn nằm an toàn trên Kafka.
• Nhược điểm: Dữ liệu có độ trễ nhất định (Eventual Consistency).

Ví dụ dự án: Khi khách đăng ký tài khoản, user-service gửi event sang Kafka để notification-service gửi email ngầm.
Cây Quyết Định (Decision Rule): Khi Nào Dùng REST? Khi Nào Dùng Kafka?
Cần kết quả tức thì để hiển thị cho người dùng ➔ DÙNG REST API:
Ví dụ: Kiểm tra số dư tài khoản, lấy chi tiết hồ sơ cá nhân, truy vấn lịch sử đơn hàng.
Tác vụ xử lý tốn thời gian, không cần chờ kết quả ngay ➔ DÙNG KAFKA EVENT:
Ví dụ: Gửi email kích hoạt, xuất hóa đơn PDF, thông báo đẩy, cập nhật dữ liệu thống kê.

📥 Consumer

Vì sao dùng Kafka thay vì gọi HTTP trực tiếp? Giảm khớp nối (Decoupling) và tăng độ bền: Nếu server gửi email bị quá tải hoặc sập tạm thời trong 15 phút, các sự kiện đăng ký tài khoản vẫn nằm an toàn trên Kafka chờ xử lý sau, người dùng đăng ký tài khoản hoàn toàn không bị gián đoạn!
PHẦN 4 • XỬ LÝ BẤT ĐỒNG BỘ

Transactional Outbox Pattern & Idempotent Consumer

Triệt tiêu hoàn toàn rủi ro Dual-Write và Đảm bảo tính nhất quán dữ liệu (Eventual Consistency)

❌ Vấn Đề Dual-Write Nếu Gọi Trực Tiếp

Khi khách đăng ký: Nếu lưu User vào Database thành công, nhưng lệnh kafkaTemplate.send() bị rớt mạng ➔ User đã tạo nhưng email không bao giờ được gửi!
Ngược lại, nếu gửi Kafka trước rồi DB bị lỗi rollback ➔ Gửi email cho tài khoản không tồn tại!

💎 Giải Pháp: Transactional Outbox Pattern

Lưu User và Sự kiện gửi email vào bảng outbox_events trong CÙNG 1 DATABASE TRANSACTION. Cả 2 cùng thành công hoặc cùng rollback! Một tiến trình ngầm định kỳ quét bảng Outbox để xuất bản lên Kafka an toàn 100%.

Quy Trình Hoạt Động Của Outbox Pattern Trong Dự Án
BƯỚC 1: CÙNG TRANSACTION
INSERT users + outbox_events
Đảm bảo dữ liệu nghiệp vụ và event luôn đồng nhất trong PostgreSQL
➔
BƯỚC 2: SCHEDULER QUÉT
FOR UPDATE SKIP LOCKED
Quét bản ghi chưa gửi mỗi 2 giây, chống tranh chấp giữa nhiều instance
➔
BƯỚC 3: XUẤT BẢN KAFKA
Đánh dấu PROCESSED
Đẩy message lên Kafka và cập nhật trạng thái đã gửi thành công
➔
BƯỚC 4: IDEMPOTENT CONSUMER
Kiểm tra eventId
Consumer bỏ qua nếu eventId đã xử lý, không bao giờ gửi trùng email
Giá trị đạt được: Đạt tiêu chuẩn phân tán At-Least-Once Delivery mà không sợ mất sự kiện ngay cả khi Kafka sập tạm thời.
PHẦN 5 • TỐC ĐỘ & BỘ NHỚ ĐỆM

Redis: Sức Mạnh In-Memory, Cấu Trúc Dữ Liệu & So Sánh PostgreSQL

Lợi ích thực tế khi đưa vào hệ thống, Các kiểu dữ liệu hỗ trợ và Bảng đối chiếu với Cơ sở dữ liệu quan hệ

⚡ 1. Lợi Ích Của Redis Khi Áp Dụng Vào Dự Án Tối ưu hệ thống
• Tốc độ siêu tốc (< 0.2ms): Lưu toàn bộ dữ liệu trên RAM, xử lý tức thì, nhanh gấp hàng trăm lần việc đọc ổ đĩa cứng (SSD/HDD).
• Giảm tải 80–90% cho PostgreSQL: Làm lớp Cache đệm (hồ sơ người dùng), giải phóng Connection Pool và tránh nghẽn DB chính khi lượng truy cập tăng vọt.
• Tự động thu dọn dữ liệu (TTL): Tự hủy key sau thời gian hết hạn (Time-To-Live, ví dụ 15 phút), không cần viết batch cronjob quét dọn rác thủ công.
• Phòng vệ cửa ngõ (Rate Limit / Brute-force): Sử dụng lệnh tăng biến đếm nguyên tử INCR để chặn đứng đợt tấn công dò mật khẩu ngay tại tầng RAM.
🧱 2. Redis Lưu Trữ Được Các Loại Dữ Liệu Nào? Data Structures
String
Chuỗi / JSON: Dùng cache hồ sơ user:profile, lưu biến đếm login:attempts (hỗ trợ lệnh INCR).
Hash
Field-Value: Lưu object nhiều trường (ví dụ user:100 -> name, role), đọc/sửa từng trường mà không cần serialize lại.
List
Danh sách thứ tự: Hoạt động như Queue (LPUSH/RPOP) để xử lý tác vụ nền hoặc lưu lịch sử thông báo gần nhất.
Set
Tập hợp duy nhất: Không trùng lặp; dùng lưu danh sách Blacklist token đã thu hồi, danh sách User Online.
Sorted Set
Tập có điểm (ZSet): Tự động sắp xếp theo Score; ứng dụng cho Bảng xếp hạng hoặc Sliding Window Rate Limiter.
⚖️ 3. Bảng So Sánh PostgreSQL vs Redis
Tiêu Chí So Sánh PostgreSQL (Relational Database) Redis (In-Memory Key-Value)
Môi trường lưu trữ Lưu trên Ổ cứng (Disk) ➔ Bền vững tuyệt đối, chuẩn ACID Lưu trên Bộ nhớ RAM ➔ Tốc độ truy xuất siêu tốc, độ trễ cực thấp
Tốc độ truy xuất Độ trễ mili-giây (5–50ms tùy độ phức tạp query và JOIN) Độ trễ micro-giây (< 0.2ms), xử lý hàng trăm ngàn req/s
Cấu trúc dữ liệu Bảng quan hệ 2 chiều (Row/Column), khóa ngoại, Schema chặt chẽ Key-Value đa cấu trúc: String, Hash, List, Set, Sorted Set linh hoạt
Vai trò trong dự án Nguồn chân lý (Source of Truth): Lưu User, Role, Tin nhắn chat Lớp đệm tốc độ & phòng vệ: Cache User, Đếm số lần đăng nhập sai
💡 Triết lý thiết kế: Dùng đúng công cụ cho đúng bài toán — PostgreSQL đảm bảo an toàn toàn vẹn dữ liệu nghiệp vụ lâu dài, còn Redis gánh tải tốc độ và dựng tường lửa phòng vệ ở cửa ngõ!
PHẦN 7 • GIAO TIẾP THỜI GIAN THỰC

WebSocket & STOMP: Chat Realtime Admin – User

Vấn đề của HTTP Polling, Kết nối hai chiều Full-Duplex và Giao thức định tuyến STOMP

💡 Vấn Đề Thực Tế Của Chức Năng Chat

• Tình huống: Khách hàng gửi câu hỏi tư vấn trên web; Admin trực trên trang quản trị cần nhận được ngay; khi Admin trả lời, khách hàng phải nhìn thấy câu trả lời tức thời mà không cần bấm F5 tải lại trang.
• Hạn chế HTTP: HTTP chỉ có cơ chế Client hỏi ➔ Server đáp. Nếu muốn cập nhật, client phải liên tục gửi request thăm dò (Polling) mỗi 2 giây, sinh ra hàng ngàn request rỗng lãng phí băng thông và nghẽn máy chủ.

⚡ Giải Pháp: WebSocket & STOMP Broker

• WebSocket: Mở và duy trì 1 kết nối TCP hai chiều (Full-Duplex) duy nhất. Server có thể chủ động đẩy (push) tin nhắn mới xuống client bất kỳ lúc nào.
• Giao thức STOMP: Quy ước định dạng khung tin và định tuyến theo Destination:
- Kênh gửi lên server: /app/chat.sendMessage
- Kênh nhận tin theo phòng: /topic/rooms.{roomId}

Tiêu chí so sánh HTTP Polling Truyền Thống WebSocket + STOMP (Dự Án Đã Làm)
Cơ chế truyền tin Client hỏi liên tục mỗi 2-3s: "Có tin mới không?" Server chủ động đẩy tin ngay khi vừa nhận được
Độ trễ (Latency) 2 - 3 giây (phụ thuộc vào chu kỳ polling tiếp theo) Mili-giây: Gần như tức thời qua kết nối TCP đang mở
Tài nguyên hệ thống Tốn băng thông mạng vì hàng ngàn header HTTP lặp lại Cực kỳ tiết kiệm CPU máy chủ và băng thông mạng
Đơn vị điều phối: Dự án sử dụng In-Memory Simple Broker tích hợp sẵn của Spring Boot kích hoạt qua config.enableSimpleBroker("/topic", "/queue") để phân phối tin nhắn nhanh chóng mà không cần cài đặt thêm broker ngoài phức tạp.

Kỹ Thuật Kết Nối & Xác Thực WebSocket STOMP

Quy trình bắt tay Handshake, Bộ chặn ChannelInterceptor xác thực JWT và Cơ chế Pub/Sub qua Simple Broker

🔌 1. Quy Trình Bắt Tay (Handshake) & Xác Thực JWT Frame CONNECT
Do WebSocket duy trì kết nối TCP lâu dài, không thể gửi header HTTP ở từng tin nhắn. Dự án giải quyết xác thực bằng 3 bước kỹ thuật chuẩn RFC:
• Bước 1 — Handshake URL: Client gọi GET /ws-chat. Server nâng cấp giao thức từ HTTP sang kết nối hai chiều HTTP 101 Switching Protocols.
• Bước 2 — Gửi Frame STOMP CONNECT: Ngay sau khi mở socket, Client gửi Frame STOMP đầu tiên đính kèm JWT:
CONNECT
Authorization: Bearer eyJhbGciOiJIUzI1Ni...
accept-version: 1.2
• Bước 3 — WebSocketAuthChannelInterceptor: Bắt sự kiện tại preSend() ➔ Giải mã token, kiểm tra hạn dùng ➔ Tạo UserPrincipal (userId, email, roles) ➔ Gán vĩnh viễn vào phiên: accessor.setUser(auth).
💬 2. Cơ Chế Pub/Sub & Bảo Mật Danh Tính @MessageMapping
Sau khi kết nối thành công, Client tương tác qua mô hình Publish - Subscribe định tuyến bởi Simple Broker trong RAM:
👂 Lắng Nghe Tin Nhắn (SUBSCRIBE):
Client gửi frame SUBSCRIBE /topic/rooms.{roomId}. Bất kỳ khi nào phòng có tin nhắn mới, Broker lập tức đẩy tin xuống tức thì (< 0.5ms).
✉️ Gửi Tin Nhắn (SEND) & Chống Giả Mạo:
Client gửi tin tới /app/chat.sendMessage. Body chỉ chứa: {"roomId": "...", "content": "..."}.
🔒 Chống giả mạo 100%: Controller tự động tiêm Principal từ phiên đã xác thực để lấy senderId. Client tuyệt đối không được tự truyền senderId!
💾 Lưu Trữ & Bắn Realtime:
ChatMessageService lưu vào PostgreSQL (bảng chat_messages) ➔ Dùng messagingTemplate.convertAndSend("/topic/rooms." + roomId, dto) đẩy tin cho cả Admin và User.
💡 Mô Hình Kết Hợp Chuẩn Doanh Nghiệp (REST API + WebSocket): Khi vừa mở khung chat, ứng dụng gọi REST GET /api/v1/chat/rooms/{roomId}/messages để tải lịch sử trò chuyện cũ từ PostgreSQL. Sau đó, ứng dụng mở kết nối WebSocket STOMP để truyền nhận các tin nhắn mới tức thời hai chiều!

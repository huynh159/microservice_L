Docker Là Gì? Bản Chất, Nhu Cầu & Khái Niệm Cốt Lõi

Chuẩn hóa đóng gói mã nguồn và xóa bỏ hoàn toàn rào cản lệch môi trường máy dev - server

⚠️ 1. Vấn Đề Thực Tế

"Trên máy tôi chạy được mà!" là bài toán đau đầu nhất khi làm phần mềm. Lệch Java 17 với 21, thiếu thư viện native trên Linux, hay cấu hình database khác nhau khiến việc chuyển giao dự án dễ đổ vỡ.

Trong dự án: Cần chạy 4 microservices backend cùng PostgreSQL, Redis, Kafka KRaft và Mailpit—tổng cộng 8 container phối hợp, nếu cài thủ công trên server thì vận hành cực kỳ rủi ro.
📦 2. Docker Giải Quyết Gì?

Docker đóng gói toàn bộ: mã nguồn chương trình, Java Runtime (JRE), thư viện phụ thuộc và biến môi trường vào một đơn vị độc lập gọi là Container. Chạy ổn định ở bất cứ nơi đâu có Docker Engine.

Lợi ích sống còn: Đảm bảo môi trường đồng nhất 100% giữa máy cá nhân của lập trình viên và máy chủ production.
🧱 3. Bốn Khái Niệm Cốt Lõi
• Image: Bản thiết kế tĩnh chỉ đọc chứa code và môi trường.
• Container: Thực thể đang chạy được sinh ra từ Image.
• Registry: Kho lưu trữ Image (Docker Hub, GitHub Registry).
• Volume: Vùng lưu trữ bền vững gắn ra ngoài máy chủ.
Áp dụng: Em gắn Volume postgres_user_data để database không bao giờ bị mất khi khởi động lại container.

Tìm Hiểu Về Dockerfile: Công Dụng & Cách Dùng Cơ Bản

Bản công thức kịch bản chỉ dẫn Docker từng bước đóng gói mã nguồn Java thành Docker Image

🎯 BA CÔNG DỤNG CHÍNH CỦA DOCKERFILE: Khuôn Mẫu Đóng Gói (Blueprint)
1. Đóng Gói Thành Image: Gộp file .jar và JRE vào một gói Docker Image tĩnh duy nhất.
2. Chạy Mọi Nơi Giống Nhau: Mọi thư viện cần thiết đều đã nạp sẵn bên trong, triệt tiêu lỗi môi trường.
3. Tự Động Hóa Dựng Môi Trường: Không cần cài đặt Java thủ công trên máy chủ, chỉ cần 1 lệnh docker build.
🛠️ Cách Dùng: 5 Chỉ Thị Cơ Bản Trong Dockerfile Java 21 JRE
# 1. Chọn môi trường nền Java 21 nhẹ
FROM eclipse-temurin:21-jre-jammy
# 2. Tạo thư mục làm việc nội bộ
WORKDIR /app
# 3. Chép file .jar đã build vào container
COPY target/user-service.jar app.jar
# 4. Mở cổng service lắng nghe
EXPOSE 8081
# 5. Lệnh khởi chạy ứng dụng
ENTRYPOINT ["java", "-jar", "app.jar"]
💡 Phân biệt dễ nhớ: Image là chiếc khuôn bánh (tĩnh, chỉ đọc); còn Container là chiếc bánh được tạo ra từ khuôn (tiến trình đang chạy).
🚀 Quy Trình 3 Bước: Từ Code Đến Container Vòng Đời Cơ Bản
Bước 1: Viết Dockerfile
Khai báo 5 chỉ thị (FROM, WORKDIR, COPY, EXPOSE, ENTRYPOINT) đặt ở thư mục gốc của service.
Bước 2: Lệnh Build tạo Docker Image
Gõ lệnh: docker build -t user-service:1.0 . ➔ Đóng gói thành Docker Image tĩnh.
Bước 3: Lệnh Run khởi chạy Container
Gõ lệnh: docker run -d -p 8081:8081 --name my-app user-service:1.0 ➔ Bật container chạy ngầm và mở cổng mạng.
🎙️ Lời Đọc A-Z:
"Để biến mã nguồn Java thành Container, bước đầu tiên là viết Dockerfile. Nó có 3 công dụng lớn ở trên cùng: Đóng gói file .jar và JRE thành Image; đảm bảo chạy ở đâu cũng giống nhau; và tự động hóa toàn bộ việc dựng môi trường.
Nhìn sang cột bên trái, trong dự án em khai báo 5 chỉ thị cơ bản: FROM chọn JRE 21 gọn nhẹ; WORKDIR đặt thư mục làm việc /app; COPY chép file jar vào; EXPOSE 8081 mở cổng nhận request; và ENTRYPOINT chạy ứng dụng với java -jar app.jar.
Quy trình 3 bước ở cột bên phải rất rõ ràng: Viết Dockerfile ➔ Gõ docker build để nướng thành Docker Image ➔ Rồi gõ docker run để biến Image thành Container đang hoạt động thực tế!"

Docker Compose: Chạy & Quản Lý Nhiều Container Bằng 1 Lệnh

Định nghĩa toàn bộ hệ sinh thái dịch vụ, mạng nội bộ và ổ đĩa lưu trữ trong file docker-compose.yml

🐙 BA GIÁ TRỊ THỰC TẾ CỦA DOCKER COMPOSE: Điều Phối Đa Container
1. Bật Toàn Bộ Cùng Lúc: Khởi chạy cả 8 container chỉ bằng đúng 1 câu lệnh docker compose up -d.
2. Tự Kết Nối Mạng Nội Bộ (DNS): Backend gọi thẳng tới DB bằng tên postgres:5432 thay vì phải mò tìm IP tĩnh.
3. Quản Lý Tập Trung: Kiểm soát thứ tự bật với depends_on (đợi DB bật trước rồi mới bật backend).
📋 Thành Phần Trong File docker-compose.yml Internal DNS
services:
  backend:
    build: ./backend
    ports: [ "8080:8080" ]
    environment:
      DB_URL: jdbc:postgresql://postgres:5432/mydb
    depends_on: [ postgres ] # Đợi DB bật trước

  postgres:
    image: postgres:17-alpine
    volumes: [ postgres_data:/var/lib/postgresql/data ]

volumes: { postgres_data: }
🚀 Các Lệnh CLI Thường Dùng Hàng Ngày Thực Hành
docker compose up -d
Khởi động tất cả container chạy ngầm
docker compose up --build -d
Build lại code mới rồi khởi chạy
docker compose down
Dừng và xóa toàn bộ container
docker compose ps
Kiểm tra trạng thái đang chạy
docker compose logs -f backend
Xem log trực tiếp để bắt lỗi
🎯 Áp dụng: Thay vì gõ 8 lệnh thủ công phức tạp, em chỉ cần gõ đúng docker compose up -d là toàn bộ hệ thống tự động khởi chạy đồng bộ.
🎙️ Lời Đọc A-Z:
"Khi số lượng container tăng lên 8 cái, việc gõ từng câu lệnh thủ công rất cồng kềnh. Vì vậy, em dùng Docker Compose qua file docker-compose.yml.
Compose mang lại 3 giá trị thiết thực: Thứ nhất, bật toàn bộ 8 container cùng lúc chỉ bằng 1 lệnh docker compose up -d; Thứ hai, tự động kết nối mạng nội bộ—nhìn vào khung code bên trái, backend gọi thẳng tới database bằng tên postgres:5432 mà không cần mò IP; Thứ ba, kiểm soát thứ tự chạy với depends_on, đảm bảo DB sẵn sàng trước khi backend bật.
Các lệnh CLI hàng ngày em thường dùng ở cột bên phải gồm up -d để chạy ngầm, up --build -d khi sửa code, và logs -f backend để theo dõi log gỡ lỗi trực tiếp!"

Spring Security: Authentication & Authorization

Phân định danh tính và quyền hạn qua chuỗi bộ lọc bảo mật SecurityFilterChain

LUỒNG XỬ LÝ REQUEST QUA SPRING SECURITY FILTER CHAIN (4 BƯỚC) HTTP 401 vs 403
1. CLIENT REQUEST
Gửi Yêu Cầu
Ví dụ: POST /api/login hoặc GET /api/admin
➔
2. FILTER CHAIN
SecurityFilterChain
Chặn bắt request, kiểm tra thông tin và quy tắc an ninh
➔
3. AUTHENTICATION
Xác Thực Danh Tính
• Đúng: Nạp SecurityContextHolder
• Sai: Chặn ngay với mã HTTP 401
➔
4. AUTHORIZATION
Kiểm Tra Quyền Hạn
• Khớp Role: Controller xử lý
• Thiếu quyền: Chặn ngay với mã HTTP 403
🔑 Phân Biệt: Bạn Là Ai? vs Bạn Được Làm Gì?
👤 Authentication (Xác thực):
Trả lời: 'Bạn là ai?' qua username/email và mật khẩu hợp lệ.
🛡️ Authorization (Phân quyền):
Trả lời: 'Bạn được làm gì?' dựa trên Role được cấp (User hay Admin).
Ví dụ phân biệt: Đăng nhập thành công nhưng vào trang quản trị bị chặn ➔ Xác thực thành công nhưng phân quyền thất bại (Server trả về HTTP 403 Forbidden).
⚙️ Cấu Hình Thực Tế Trong Spring Boot 3 SecurityConfig
http.authorizeHttpRequests(auth -> auth
  .requestMatchers("/api/auth/**").permitAll()
  .requestMatchers("/api/admin/**").hasRole("ADMIN")
  .anyRequest().authenticated()
);
• permitAll(): Cho phép gọi công khai mà không cần đăng nhập.
• hasRole("ADMIN"): Yêu cầu tài khoản bắt buộc phải có vai trò Quản trị viên.
• authenticated(): Yêu cầu bắt buộc phải đăng nhập hợp lệ.
🎙️ Lời Đọc A-Z:
"Bước sang Phần 2 về Bảo mật, em phân định rạch ròi hai khái niệm cốt lõi ở cột bên trái: Authentication là xác thực 'Bạn là ai?' qua email và mật khẩu; còn Authorization là phân quyền 'Bạn được phép làm gì?' qua Role.
Nhìn vào sơ đồ luồng 4 bước ở trên cùng: Khi request đi vào, SecurityFilterChain sẽ chặn bắt. Nếu chưa đăng nhập hoặc sai pass, hệ thống từ chối ngay với mã HTTP 401 Unauthorized. Nếu đã xác thực nhưng tài khoản User thông thường cố truy cập endpoint của Admin, hệ thống phát hiện thiếu quyền và trả về HTTP 403 Forbidden.
Trong mã nguồn ở cột bên phải, em cấu hình .permitAll() cho API đăng ký đăng nhập; .hasRole(\"ADMIN\") cho API quản trị; và .authenticated() cho mọi API yêu cầu đăng nhập!"

JSON Web Token: Cấu Trúc 3 Phần & Chiến Lược Dual-Token

Bản chất Stateless, Chữ ký số HMAC-SHA256 chống giả mạo và Cặp Access/Refresh Token

🧩 Cấu Trúc JWT Gồm 3 Phần Nối Bằng Dấu Chấm Base64URL
HEADER . PAYLOAD . SIGNATURE
1. Header (Màu hồng): Khai báo thuật toán ký, ví dụ {"alg":"HS256","typ":"JWT"}.
2. Payload (Màu xanh dương): Chứa Claims như userId, roles, hạn dùng exp. ⚠️ Chỉ là encode Base64URL nên ai cũng đọc được, tuyệt đối không chứa password!
3. Signature (Màu xanh ngọc): Chữ ký số HMAC-SHA256 tạo từ SecretKey. Nếu hacker tự sửa role từ USER lên ADMIN trong Payload, chữ ký sẽ sai lệch ngay và server từ chối lập tức.
⚖️ Chiến Lược Dual-Token (Cân Bằng Bảo Mật & UX) Bảo Vệ Đa Lớp
Tiêu Chí Access Token Refresh Token
Thời gian sống Ngắn hạn: 15 phút (hạn chế rủi ro lộ) Dài hạn: 7 ngày (trải nghiệm mượt mà)
Lưu trữ Stateless: Server không lưu DB, chỉ kiểm tra chữ ký Stateful: Lưu bản băm SHA-256 trong Database để thu hồi
Mục đích Gắn vào Header Bearer cho mọi API nghiệp vụ Chỉ gửi lên /api/auth/refresh để đổi token mới
🎯 Trải nghiệm người dùng: Khi Access Token hết hạn, ứng dụng tự động dùng Refresh Token xin cấp token mới mà khách không bị văng ra bắt đăng nhập lại.
🎙️ Lời Đọc A-Z:
"Trong môi trường Microservices phân tán, em không dùng Session vì sẽ gây dính máy chủ. Em dùng JWT Stateless.
Nhìn sang cột bên trái, một chuỗi JWT gồm 3 phần nối bằng dấu chấm: Header khai báo thuật toán; Payload chứa thông tin định danh như userId và role—Thầy Cô lưu ý: Payload chỉ encode Base64URL nên ai cũng đọc được, tuyệt đối không lưu mật khẩu ở đây; và Signature là chữ ký số HMAC-SHA256 kết hợp SecretKey, nếu hacker cố sửa quyền từ USER lên ADMIN thì chữ ký sẽ sai lệch và server từ chối ngay!
Ở cột bên phải, để cân bằng giữa bảo mật và trải nghiệm, em áp dụng cơ chế Dual-Token: Access Token sống ngắn 15 phút stateless hoàn toàn; còn Refresh Token sống dài 7 ngày lưu bản băm trong Database để tự động gia hạn token mà không bắt người dùng đăng nhập lại!"

Microservices: Phân Rã Kiến Trúc & 3 Lợi Ích Cốt Lõi

Khắc phục điểm nghẽn sập dây chuyền của Monolith và triển khai chuẩn Database-per-Service trong dự án

🏢 Hạn Chế Của Kiến Trúc Monolith

Toàn bộ tính năng User, Chat, Notification đóng gói chung vào một file jar duy nhất và trỏ vào 1 Database dùng chung.
Hạn chế chí mạng: Chỉ cần một module Chat bị rò rỉ bộ nhớ hoặc khóa bảng database, toàn bộ hệ thống sẽ bị kéo sập theo, khiến chức năng Đăng nhập hay Thanh toán cũng tê liệt hoàn toàn!

🚀 3 Lợi Ích Cốt Lõi Của Microservices
• 1. Cách ly lỗi (Fault Isolation): Chat Service bị lỗi thì User Service vẫn vận hành 100% bình thường.
• 2. Triển khai độc lập (Independent Deployment): Cập nhật phòng chat không cần tắt cả hệ thống để deploy lại.
• 3. Mở rộng linh hoạt (Targeted Scalability): Khi lượng chat tăng vọt, chỉ cần nhân bản riêng container Chat Service.
Tiêu chí so sánh Monolith (Kiến Trúc Nguyên Khối) Microservices (Kiến Trúc Dự Án)
Cơ sở dữ liệu 1 Database chung (khóa bảng ảnh hưởng lẫn nhau) Database-per-Service: User và Chat sở hữu Database riêng biệt (users_db, chat_db)

Giao Tiếp Giữa Các Service: Sync REST vs Async Kafka

Cây quyết định lựa chọn cơ chế giao tiếp phù hợp với từng bài toán nghiệp vụ

📞 Đồng Bộ: Synchronous (REST API)

Bên gửi gửi request HTTP và phải chờ đợi bên nhận phản hồi mới tiếp tục công việc.
• Ưu điểm: Đơn giản, nhận ngay kết quả để render giao diện.
• Nhược điểm: Khớp nối chặt (Tight Coupling); nếu service nhận bị chậm sẽ làm nghẽn luôn service gửi.

Ví dụ dự án: Khi Admin mở phòng chat, chat-service gọi HTTP GET sang user-service để lấy tức thì họ tên và avatar khách hàng.
📨 Bất Đồng Bộ: Asynchronous (Apache Kafka)

Bên gửi bắn sự kiện vào hàng đợi rồi tiếp tục ngay lập tức mà không cần chờ đợi.
• Ưu điểm: Tách rời hoàn toàn (Decoupled); nếu bên nhận tạm chết thì sự kiện vẫn nằm an toàn trên Kafka.
• Nhược điểm: Dữ liệu có độ trễ nhất định (Eventual Consistency).

Ví dụ dự án: Khi khách đăng ký, user-service gửi event sang Kafka để notification-service kéo về gửi email ngầm.
CÂY QUYẾT ĐỊNH KIẾN TRÚC: KHI NÀO DÙNG REST? KHI NÀO DÙNG KAFKA?
Cần kết quả tức thì để hiển thị UI ➔ DÙNG REST API:
Ví dụ: Truy vấn hồ sơ người dùng, lấy lịch sử chat cũ, kiểm tra trạng thái đơn.
Tác vụ xử lý tốn thời gian, chạy ngầm ➔ DÙNG KAFKA EVENT:
Ví dụ: Gửi email kích hoạt tài khoản, thông báo đẩy, ghi log thống kê.

Transactional Outbox Pattern & Idempotent Consumer

Triệt tiêu hoàn toàn rủi ro Dual-Write và Đảm bảo tính nhất quán dữ liệu phân tán

❌ Vấn Đề Dual-Write Nếu Gọi Trực Tiếp

Khi khách đăng ký: Nếu lưu User vào Database thành công, nhưng lệnh gửi Kafka bị rớt mạng ➔ User đã tạo nhưng email không bao giờ được gửi!
Ngược lại, nếu gửi Kafka trước mà DB bị lỗi rollback ➔ Lại gửi email cho một tài khoản ảo không tồn tại!

💎 Giải Pháp: Transactional Outbox Pattern

Lưu User và Sự kiện gửi email vào bảng outbox_events trong CÙNG 1 DATABASE TRANSACTION. Cả 2 chỉ có thể cùng thành công hoặc cùng rollback!
Một tiến trình Scheduler định kỳ quét bảng Outbox để xuất bản lên Kafka, cam kết không làm mất sự kiện.

QUY TRÌNH 4 BƯỚC HOẠT ĐỘNG CỦA OUTBOX PATTERN TRONG DỰ ÁN
BƯỚC 1: CÙNG TRANSACTION
INSERT users + outbox_events
Đảm bảo dữ liệu User và event luôn đồng nhất trong PostgreSQL
➔
BƯỚC 2: SCHEDULER QUÉT
FOR UPDATE SKIP LOCKED
Quét bản ghi chưa gửi mỗi 2s, chống tranh chấp giữa nhiều instance
➔
BƯỚC 3: XUẤT BẢN KAFKA
Đánh dấu PROCESSED
Đẩy message lên Kafka và cập nhật trạng thái đã gửi thành công
➔
BƯỚC 4: IDEMPOTENT
Kiểm tra eventId
Consumer bỏ qua nếu eventId đã xử lý, chống gửi trùng 2-3 email
🎙️ Lời Đọc A-Z:
"Đây là một trong những điểm kỹ thuật quan trọng nhất của bài seminar: Giải quyết bài toán Dual-Write.
Nhìn vào thẻ màu đỏ: Nếu ta lưu User vào DB thành công, sau đó mới gọi lệnh gửi Kafka mà chẳng may mạng rớt, thì User đã tạo nhưng email không bao giờ được gửi. Ngược lại, nếu gửi Kafka trước mà DB bị lỗi rollback, thì lại gửi email cho một user không tồn tại!

Redis: Sức Mạnh In-Memory, Cấu Trúc Dữ Liệu & So Sánh PostgreSQL

Lợi ích thực tế khi đưa vào hệ thống, Các kiểu dữ liệu hỗ trợ và Bảng đối chiếu với Database quan hệ

⚡ 1. Bốn Lợi Ích Của Redis Trong Dự Án In-Memory RAM
• Tốc độ truy xuất sub-millisecond: Lưu toàn bộ trên RAM, giảm thiểu tối đa độ trễ so với đọc từ ổ đĩa cứng.
• Giảm tải cho PostgreSQL: Làm lớp Cache đệm cho thông tin hồ sơ người dùng (user:profile).
• Tự động thu dọn dữ liệu (TTL 15 phút): Tự hủy key hết hạn, không cần viết cronjob dọn rác thủ công.
• Phòng vệ Brute-force: Dùng lệnh tăng biến đếm nguyên tử INCR để chặn đứng các đợt dò pass ngay tại tầng RAM.
🧱 2. Các Kiểu Dữ Liệu Hỗ Trợ Data Structures
• String: Cache hồ sơ JSON, đếm số lần đăng nhập sai (hỗ trợ lệnh INCR).
• Hash: Lưu object nhiều trường (ví dụ user:100 -> name, role).
• List: Hoạt động như Queue (LPUSH/RPOP) xử lý tác vụ nền.
• Set: Tập hợp không trùng lặp, lưu Blacklist token đã thu hồi.
• Sorted Set: Sắp xếp theo Score, dùng cho Bảng xếp hạng hoặc Rate Limiter.
Tiêu Chí So Sánh PostgreSQL (Relational Database) Redis (In-Memory Key-Value)
Môi trường lưu trữ Lưu trên Ổ cứng (Disk) ➔ Bền vững tuyệt đối, chuẩn ACID Lưu trên Bộ nhớ RAM ➔ Tốc độ truy xuất siêu tốc, độ trễ cực thấp
Tốc độ truy xuất Độ trễ mili-giây (5–50ms tùy độ phức tạp query) Độ trễ ở mức sub-millisecond (dưới 1 mili-giây trên RAM)
Vai trò trong dự án Nguồn chân lý (Source of Truth): Lưu User, Role, Tin nhắn chat Lớp đệm tốc độ & phòng vệ: Cache User, Đếm số lần nhập sai pass

WebSocket & STOMP: Chat Realtime Admin – User

Vấn đề của HTTP Polling, Kết nối hai chiều Full-Duplex và Giao thức định tuyến STOMP

💡 Hạn Chế Của HTTP Polling Truyền Thống

• Tình huống: Khách hàng hỏi Admin cần nhận được ngay; khi Admin trả lời khách hàng phải nhìn thấy tức thời mà không cần bấm F5 tải lại trang.
• Hạn chế HTTP: Chỉ có cơ chế Client hỏi thì Server mới trả lời. Trình duyệt phải liên tục gửi request thăm dò (Polling) mỗi 2 giây, sinh ra hàng ngàn request rỗng gây lãng phí băng thông và nghẽn máy chủ.

⚡ Giải Pháp: WebSocket & STOMP Broker

• WebSocket: Duy trì 1 kết nối TCP hai chiều (Full-Duplex) duy nhất. Server có thể chủ động đẩy (push) tin nhắn mới xuống client bất kỳ lúc nào.
• STOMP: Quy ước định tuyến theo Destination:
  - Gửi tin lên server: /app/chat.sendMessage
  - Nhận tin theo phòng: /topic/rooms.{roomId}

Tiêu chí so sánh HTTP Polling Truyền Thống WebSocket + STOMP (Dự Án Đã Làm)
Cơ chế truyền tin Client hỏi liên tục mỗi 2-3s: "Có tin mới không?" Server chủ động đẩy tin ngay khi vừa nhận được
Độ trễ (Latency) 2 - 3 giây (phụ thuộc vào chu kỳ polling) Mili-giây: Gần như tức thời qua kết nối TCP đang mở
Tài nguyên hệ thống Tốn băng thông mạng vì hàng ngàn header HTTP lặp lại Cực kỳ tiết kiệm CPU máy chủ và băng thông mạng
Đơn vị điều phối trong dự án: Sử dụng In-Memory Simple Broker tích hợp sẵn của Spring Boot kích hoạt qua enableSimpleBroker("/topic") để phân phối tin nhắn cực nhanh trên RAM mà không cần cài thêm hạ tầng phức tạp.

Kỹ Thuật Kết Nối & Xác Thực WebSocket STOMP

Quy trình bắt tay Handshake, Bộ chặn ChannelInterceptor xác thực JWT và Cơ chế chống giả mạo

🔌 1. Quy Trình Bắt Tay & Xác Thực JWT (3 Bước) Frame CONNECT
• Bước 1 — Handshake: Client gọi GET /ws-chat. Server nâng cấp giao thức HTTP sang WebSocket qua mã HTTP 101 Switching Protocols.
• Bước 2 — Frame STOMP CONNECT: Client gửi frame STOMP đầu tiên đính kèm JWT Bearer Token trong header.
• Bước 3 — ChannelInterceptor: Lớp chặn preSend() giải mã token, kiểm tra hạn và gắn đối tượng xác thực vào phiên qua accessor.setUser(auth).
💬 2. Cơ Chế Pub/Sub & Bảo Mật Danh Tính @MessageMapping
• Lắng nghe (SUBSCRIBE): Client gửi SUBSCRIBE /topic/rooms.{roomId} để nhận tin tức thời.
• Gửi tin (SEND): Client gửi lên /app/chat.sendMessage. Body chỉ chứa nội dung và mã phòng.
🔒 Chống giả mạo 100%: Controller tự động trích xuất danh tính người gửi trực tiếp từ Principal của phiên kết nối. Client tuyệt đối không được tự truyền senderId!
• Lưu trữ & Bắn tin: Lưu vào PostgreSQL (chat_messages) ➔ Bắn tin qua messagingTemplate.
💡 Mô hình kết hợp chuẩn doanh nghiệp (REST + WebSocket): Khi vừa mở khung chat, ứng dụng gọi REST API để tải lịch sử trò chuyện cũ từ PostgreSQL. Sau đó, ứng dụng mở kết nối WebSocket STOMP để truyền nhận các tin nhắn mới tức thời!
🎙️ Lời Đọc A-Z:
"Do kết nối WebSocket không truyền header HTTP trên từng tin nhắn, em xử lý xác thực theo 3 bước chuẩn công nghiệp ở cột bên trái:
Bước 1: Client gửi yêu cầu Handshake nâng cấp kết nối HTTP sang WebSocket qua mã HTTP 101 Switching Protocols.
Bước 2: Client gửi frame STOMP CONNECT đầu tiên đính kèm JWT Bearer Token.
Bước 3: Lớp chặn WebSocketAuthChannelInterceptor giải mã token, kiểm tra tính hợp lệ và gắn đối tượng xác thực vào phiên qua accessor.setUser().
Ở cột bên phải - Điểm mấu chốt về an ninh: Khi gửi tin nhắn, người dùng không được phép tự truyền senderId. Controller tự động trích xuất danh tính trực tiếp từ Principal của phiên, loại bỏ 100% rủi ro mạo danh người khác để gửi tin nhắn rác!
Và ở khung dưới cùng: Khi mở khung chat, ứng dụng gọi REST API để tải lịch sử cũ từ DB, sau đó mở WebSocket để truyền nhận tin mới tức thời!"
